# AudiPick 智能合同审阅迁移差异记录

基线：`modules/AudiPick/`（Electron 31 + 原生 JS，约 6,663 行，无 React、无打包器）。
目标：`src-tauri/src/audipick.rs` + `storage.rs` 的 AudiPick 表 + `src/AudiPickPage.tsx`。

**这也是 2026-08-05 之前没有任何迁移文档的工具**，且新旧技术栈完全不同、后端最薄、前端最重。

## 规则层：只同步新版实际加载的那一部分

`index.html` 用 script 标签加载的只是规则包的一个子集：13 个 `prompts/*.js`、`registry.js`、
`revenue_workpaper.js`、`fieldset.js`。**`ui.js`、`classify.js`、`theme.js` 不加载**——
它们是旧 Electron 外壳的界面代码，React 版自己重写了这部分。
旧栈 1.4.6 新增的 `ai_response.js`、`export_naming.js`、`loan_audit.js` 同样只被 `audipick.html` 引用，
规则文件之间无依赖，因此也不在同步范围内。

加载顺序有约束：`revenue_workpaper.js` 必须排在 `prompts/revenue_workpaper.js` 之前，
因为提示词在加载期读取前者设置的 `REVENUE_WORKPAPER_QUESTIONS` 来拼「底稿问题目录」。
（此前顺序相反，该目录一直是空的，见下节。）

## 2026-08-05 已修复

- **长合同不分段**：旧版超一万字自动切成 8000 字一段、段间续接页码标记、3 段并发；
  新版整篇一次性发出且未设输出上限。后果是超长合同要么报错，要么**模型只读了前半段、后半段契约条款静默漏提**，
  而界面照样显示"提取成功，返回 N 条"。已按旧版切分（含页码标记续接），并补单元测试锁定"不丢内容""每段带页码标记"。
- **收入底稿两阶段问答缺失**：旧版先对资料包每份文件抽取**不含会计结论的客观事实**（付款条件、交付验收、
  退货回购、返利折扣、是否引用 SOW）形成共享事实表，再把 43 道题分 5 批作答并用事实表回填
  （如按付款期限天数自动判定"是否存在重大融资成分"，资料包缺 SOW 时降级为需复核）。
  新版曾与其余 12 个模板走同一条路：整份文本 + 原始提示词一次性问 43 题，几乎必然漏答或被截断。已重建两阶段流程。
- **收入底稿导出丢失填列映射**：旧版导出 25 个中文列，含**工作表名称、底稿行号、回答/理由/摘录三个目标单元格**——
  这份映射正是该模板的核心价值；新版按字母序输出英文原始键名，清单从"可执行的填列指令"退化为"需人工重新定位的原始数据"。
  映射数据本就在规则文件里且已加载，只是导出时未调用。已接上（导出支持调用方指定列顺序）。
- **"待补资料"永远显示占位文字**：规则模块输出 `text` / `questionNos` / `blocking`，界面却先读 `title`，
  每条都落到兜底文案"需要补充支持资料"。数字是对的，内容全是废话。已修正并显示涉及题号与是否阻塞。
- **"自动不适用"过滤未生效**：合同无回购条款时其两道子问题应被隐藏，规则已打标记，展示与导出都不读。已生效。
- **删除项目/文件无二次确认**：点击即删，连带该项目全部 PDF、提取结果与复核标记，无撤销。
  （全应用此前仅 Roll Forward 有三处确认。）已补，并写明会一并删除什么。
- **文档类型自动识别整体缺失**：模板下拉永远停在"借款·限制性契约"，选错不会有任何提示。
  旧版 `classify.js` 依赖 Electron 全局与自有 HTTP，无法直接移植；改为复用现有 `audipick.classify` 接口、
  在前端按当前模板清单动态拼提示词。**采用"给建议 + 人工确认"而非静默切换**，模型返回不存在的模板 id 时退回当前模板。
- **证据页跳转不看来源文件**：资料包场景下会在当前打开的 PDF 上跳页，看到的是无关内容，
  用户会以为模型编造了证据。现按结果的来源文件字段匹配到对应 PDF 再跳（按文件名长度倒序匹配，
  避免"主合同.pdf"抢走"主合同补充协议.pdf"的引用）。
- **无提取缓存**：同一合同、同一模板、同一字段组合重复提取会再烧一遍 token，且因模型随机性结果还不一样。
  已按"合同 + 模板 + 字段组合 + 上下文内容指纹"缓存，关联资料一变即失效。
- **调用失败不重试**：批量跑 30 份，网络抖动就有几份失败需手动找出重跑。已加 3 次重试并显示剩余次数。
- **批量提取失败清单不显眼**：worker 逐份回报成功/失败与原因，界面只显示进度条。已单独列出。
- **请求缺少关键参数**：旧版每次调用都下发 `thinking:{type:disabled}` 与（DeepSeek 下）`response_format`，
  迁移时两个都漏了，推理型模型会先跑思维链再吐 JSON。与 FA List 同一处病根，已一并修复。
- **错误信息不可诊断**：与 `fa.rs` 相同的"先解析 JSON 再判状态"问题，已改为先取文本、再判状态、最后解析。

## 仍未清零

- **浏览器本地 Tesseract 与任意第三方 OCR 配置仍未恢复**：当前已有统一 AI 视觉、百度高精度和固定的
  本机服务 `127.0.0.1:8765` 三条路；其中本机服务不向外部发送合同图片，但仍需用户自行启动兼容服务。
- **OCR 无法单独配置视觉模型**，只能复用工具箱全局 LLM。
- **版本差异目前通过版本下拉逐版查看**，尚未做两版并排字段对比和差异高亮。
- **通用模板导出仍用英文键名、按字母序**，且金额为文本（旧版用中文标签、识别金额列并套千分位）。
- **批量提取仍要求先生成每份 PDF 的文字层**；现在打开文档即自动保存，启动批量前也会列出尚未读取的文件，但尚未把整项目 OCR 自动编入后台任务。
- **拖放文件仍未开放**：当前已恢复多选 PDF 与递归选择文件夹；出于路径白名单约束，尚未直接接收系统拖放路径。
- **旧数据迁移预计丢四样**（未实机验证）：导入的 PDF 描述信息写空导致文件列表读取报错、
  历史提取结果因字段组合标识算法不同被全部过滤（数据在库但看不见；2026-08-09 改按
  「最近一次提取的字段集」取数后应已缓解，但迁移路径本身仍未实机验证）、补充资料从属关系丢失、
  合同文字不在备份内需重读（扫描件要重跑 OCR）。

## 新版明确更好

完全离线可用（旧版界面样式与浏览器 OCR 依赖境外 CDN）、密钥进 Windows 凭据管理器
（旧版明文存 localStorage）、备份改为 zip + 逐 PDF 哈希校验 + 导入失败整体回滚
（旧版把所有 PDF 转 base64 塞进单个 JSON，几十份即撑爆内存且零校验）、
批量任务跑在独立进程可真正暂停/取消/崩溃隔离。

### 另外两处从 1.4.6 补回来的

- **导出文件名预填**（对应旧栈 `rules/export_naming.js`）：保存对话框原先是空文件名，
  每次导出都要手打、事后也分不清哪个是哪个。现按旧版规则预填
  `合同名_模板名_日期.xlsx`（无单份合同时退化为 `项目_客户_范围_类型_日期`），
  并做 Windows 非法字符替换、保留字规避和 180 字截断——合同名里常见的 `/` `:` 会让保存直接失败。
  实现落在 `audipickUi.ts` 的 `audipickExportName`，已与旧栈 `defaultExportName` **逐用例实跑比对一致**
  （含"保留字加了日期后不再触发转义""无任何标识时只剩日期"这两个反直觉分支）。
  同时接到迁移备份的 zip 导出上。基础设施本来就支持（`pickPath` 第四个参数、FA List 早已在用），
  只是 AudiPick 没传。
- **模型返回空正文不再静默变成"0 条"**（对应旧栈 `rules/ai_response.js` 的 `emptyContentError`）：
  `audipick.rs` 原先把缺失的 `message.content` 兜底成 `""`，解析出零条目正常返回，
  用户看到的是"提取到 0 条"，与"这份合同确实没内容"无法区分。
  现改为抛 `EMPTY_ASSISTANT_CONTENT`，并带上 `finish_reason` 与思维内容长度
  （`finish_reason=length` 时明确提示"输出额度已用尽"）。
  `ai_response.js` 的另一半能力（关闭思维链、DeepSeek JSON 模式）Rust 侧早已实现，无需移植。

### 已确认不需要改的

`src-tauri/src/audipick.rs` 对 LLM 返回的字段名零硬编码（导出列取行 key 并集，
`parse_json_content` 不认字段名），三个新提示词的输出仍是 `{"items":[...]}`，因此后端一行未动。
`window.FieldSet` React 侧未使用，`fieldset.js` 新增的字段迁移分支在新栈里是死代码。

### 附表二轮追问已接入（对照 `modules/AudiPick/audipick.html:1695-1757`）

主问题作答后原本直接落库，新版规则提供的三个追问阶段无人调用。现已在
`extractRevenueWorkpaper` 里按旧栈顺序接上：

1. **履约义务时点逐项判断**（`buildPerformanceObligationTimingQuestions`）——
   主问题识别出履约义务后，第 5a 步的时段/时点问题按 PO 逐项重问；
   回答后剔除 `current` 里题号 5.1 且工作表形如 `第5a步（PO#N）` 的旧行，用新答案取代。
2. **附表条件问题递归追问**（`buildTriggeredDetailQuestions`）——
   附表回答会触发新的附表问题，循环追问至某轮不再产生新问题；超过 8 轮抛错，
   文案沿用旧版「附表条件问题超过最大展开层级…」。
3. **同类履约义务一致性复核**（`buildPoConsistencyReviewQuestions`）——
   控制权转移模式相同的 PO 若答案打架，按相同指标统一重问，
   并用 `revenueQuestionKey` 替换掉原答案。

三个阶段共用 `answerGroup`：先整组问，`missingRevenueTargets` 找出模型漏答的，
每 3 题一组重问，仍然漏的生成 `technical_fallback` 占位行并标记「需人工复核」——
**这些占位行同时是递归的收敛保证**：占位行带着目标题号入库后，下一轮
`buildTriggeredDetailQuestions` 就不会再返回该题。已实测「模型一题不答」的最坏情况下
递归在下一轮收敛，不会空转到 8 轮上限。

与旧栈一致，追问轮次喂给模型的是**共享事实表**（超过 7 万字符按旧版规则截断），
不是合同全文；事实表本身已带来源文件与页码。

顺带补上了主问题作答后缺失的 `normalizeResults`——此前只做 `mergeRevenueAnswers`，
新版的结构化明细展开（`performance_obligations` / `appendix_subjects` 展开成附表行）
在主路径上根本没跑起来。

结果面板新增 `followUpItems`，显示追问阶段额外产生的行数。

### 1. 首页

便携版金标：`pgHome()` 是没有左侧栏的独立落地页；顶部 64px 黑色栏含 AudiPick 品牌、“配置”和
“开始使用”，中间是 A 标志、产品名、“智能合同审计助手”、说明及“开始审计”，底部是“批量上传PDF / AI智能提取 /
导出工作底稿”三张能力卡。品牌点击返回首页的入口在 `audipick.html:2880`。

React 开工前：启动即进入产品壳与工作台，左侧品牌不可进入首页；`viewMode` 没有 `home`。

验收点：

- 首次打开 AudiPick 独立窗口时显示首页，不直接显示项目工作台。
- 首页不出现工作台侧栏；标题、说明、三个能力卡及两个顶部按钮的位置和层级与 `pgHome()` 一致。
- “配置”进入 AudiPick 配置页；“开始使用 / 开始审计”进入工作台；进入应用后点侧栏品牌可返回首页。

### 2. 工作台 / 项目列表

便携版金标：`projectProgressInfo()`、`projectPhaseBadge()`、`projectDashboardRows()`、
`projectDashboardCardHtml()`（`audipick.html:3026-3128`）共同生成一行一个项目的管理列表。每行含：

- 项目名、客户、项目日期、业务阶段徽标（未上传 / 待提取 / 待复核 / 复核完成 / 结果需更新）；
- 用户管理的项目状态下拉框；
- “提取 x/y · 复核 x/y”、完成百分比和进度条；
- 最近更新时间、“继续”按钮与 `•••` 删除菜单；
- 搜索、状态筛选、顶部三个可点击统计卡，以及 `pgDash():3140` 定义的 12 种排序；
- `ocrResumeBannerHtml()` 显示未完成 OCR、已保存页数、“放弃任务 / 继续识别”。

React 开工前：项目显示为三列 `ap-project-card`；仅显示状态、项目/客户、文件数、结果数、日期和 30 天提示；
没有业务阶段、提取/复核进度、最近更新、“继续”和更多菜单；排序只有 6 种，且使用项目日期而不是最近活动。

验收点：随机准备“空项目、待提取、待复核、复核完成、关联资料更新”五种数据，逐个确认阶段徽标、计数和进度；
12 种排序分别验证首尾项目；项目状态下拉不应被系统进度自动覆盖；OCR 中断后重开应用应出现恢复横幅。

### 3. 新建项目

便携版金标：`np()` 打开 `#modal-root` 居中模态框，字段自上而下为项目名称、客户名称、批量提取首选模板

React 开工前：表单位于工作台 `<details>` 中；默认模板必须有值；只校验项目名；创建后直接进入项目详情；没有取消按钮、
遮罩关闭和自动聚焦。

验收点：按钮、遮罩、Esc/遮罩关闭策略、字段顺序、可选模板、默认日期、首输入框焦点和双字段校验与金标一致；

### 5. 合同详情与工作底稿

便携版金标是两个连续页面，而不是一个长表单：

1. `pgCont()`：面包屑、返回、文件名、字数/识别方式/累计结果、预览 PDF、AI 状态；随后是
   `fileFlowCardHtml()` 的三步流程——模板确认（AI 建议、置信度、人工确认）、字段选择与提取、底稿查看与导出；
   再显示当前模板条数、合同字数、已用模板数、识别方式四项统计，以及可折叠并可保存/复制的合同文本。
2. `pgWork()` + `workpaperHtml()`：模板和底稿版本切换、导出当前/全部底稿、关键词筛选、左侧条目表、右侧单条详情、
   复核状态与证据跳页；收入底稿还带资料包和待补资料区。
3. 两页均可按需打开 PDF 左栏；`splitPaneHtml()` / `initSplitPane()`（`audipick.html:2792-2825`）提供可拖动的
   25%–65% 分栏并记住比例。PDF 工具栏含前后页、页码直达、原文搜索上下一个和高亮。

React 开工前：模板选择、关联资料、OCR、保存文字、单份/批量提取、PDF canvas、文本 textarea 和结果卡片从上到下串在
同一页；没有“合同详情 → 查看底稿”路由层级，没有可调双栏，没有条目表 + 详情阅读器。结果虽可编辑、标记复核、跳证据和
切换历史版本，但交互形态不等同于便携版。

验收点：从项目详情点一份文件必须先到合同详情；三步处理卡状态随模板确认、提取完成正确变化；点击“查看底稿”进入工作底稿；
PDF 左栏可开关、拖宽并跨刷新保留比例；证据来自关联文件时自动换到正确 PDF；表格筛选、版本切换、行选择、复核、编辑和
当前/全部导出均可用。

### 6. 提取模板库

便携版金标：`pgRules()` 是“页头 + 新增模板按钮 + 五分类 Tab + 搜索 + 42% 卡片列表 + 右侧模板详情”；
空“我的模板”有专门引导。`openBlankRuleModal()`、`copyRuleAsCustom()` 以模态框收集名称/文档类型，再进入编辑；
内置模板只读且可复制，自定义模板可编辑、删除。详情必须展示版本、文档类型、来源、描述、适用场景、字段、示例及折叠的
Prompt / JSON 结构。

React 开工前：分类、搜索、卡片/详情、字段、示例、Prompt、复制/编辑/删除基本存在；但“新增模板”被放在右侧折叠区，
新增/复制不是金标模态流程，左右列宽、空状态和卡片信息层级尚未逐像素对齐。因此只能判“部分”。

验收点：五个 Tab、搜索保持焦点、空状态、42%/58% 双栏、选中卡片、只读/自定义按钮状态及三个模板模态流程逐项一致；
规则数据仍来自当前工具箱内置资源和 SQLite 自定义规则，不恢复旧 localStorage。

### 7. 配置

便携版金标：`pgCfg()` 顶部有“提取AI / 桌面网络 / OCR引擎 / OCR状态”四卡，以及“OCR引擎 / AI模型”Tab。
AI 页具有独立 API Key、Base URL、Model、Thinking、保存和测试并保存。OCR 页具有 AI 视觉、浏览器 Tesseract、第三方 OCR
三张单选卡；AI 视觉有独立模型三字段；第三方 OCR 有预设、URL、四种鉴权、AK/SK 或 Token、请求格式、返回字段路径、
保存和可用性检测。

React 开工前：AudiPick 侧栏没有配置入口。工具箱统一设置已有 LLM 测试/保存，以及“统一 AI / 百度 OCR / 本机 OCR 服务”
三种 OCR 底层（`App.tsx:1331-1352`、`1683-1731`），但页面结构与可配置范围不等同；浏览器 Tesseract、独立视觉模型和
任意第三方 OCR 配置不存在。

验收点：AudiPick 内必须有与金标同位置的配置入口和页面；能由工具箱统一底层承载的字段读取/写入工具箱设置及凭据管理器；
工具箱明确不支持的旧引擎必须显示真实限制或实现安全适配，不能画出可点击但无效的假控件。

### 本轮最终验收门禁

1. 在 `1480 × 920` 的 AudiPick 独立 Tauri 窗口逐页截图，与便携版在相同尺寸、相同假数据下并排核对；最小尺寸也要验证
   `1080 × 700` 不遮挡主操作。旧 Electron 默认窗体为 `1440 × 920`、最小 `1120 × 720`（根目录 `main.js:22-25`）。
2. 逐页核对上述路由层级和交互形式，不接受“功能在别处也能做”作为页面同等。
3. 独立窗口保持工具箱主题、SQLite、Rust 命令、任务事件和凭据管理器；不得引入第二套 localStorage 项目数据、Electron IPC、
   浏览器直连 LLM 或 CDN 运行依赖。
4. 自动化至少覆盖：首页路由、新建模态、工作台阶段/排序、项目文件分组、合同→底稿跳转、日志抽屉不改路由、导览状态、
   借款中心显示条件；再用一份脱敏真实合同完成端到端人工验收。
5. 最终交付必须把本表每项更新为“同等 / 有意差异 / 未完成”，其中“有意差异”必须写明是工具箱底层约束并获得用户确认。
