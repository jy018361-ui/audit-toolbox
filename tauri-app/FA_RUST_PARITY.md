# FA List Rust 迁移覆盖矩阵

本矩阵以 `tools/fa_list` 的 Python 内核与 `audit_engine/handlers.py` 的实际生产路由为基线。Rust 实现在 `src-tauri/src/fa.rs`，生产路径不调用 Python、PowerShell 或 Excel COM。

## 仍需正式样例验证/补齐后才可宣称完全等价

### 2026-08-09 长期资产明细新旧输出对比

- 对比文件：旧版 `旧代码输出-FA_List_20260808_213955.xlsx`，新版 `新代码-FA_List_20260809_135119.xlsx`。两者 Sheet 集合一致，期末 FA List 均为 5,499 张，原值 871,318,110.94、累计折旧 251,439,019.31，说明期末读取与金额主干一致。
- 核心差异不是计算公式，而是期初工作表不同：旧版读 `固定资产明细 241231`（5,449 张），新版误选首页 `Data`（6,295 张）。因此新版将 842 张仅期初卡片识别为处置，处置清单从 26 行/85,627.81 放大到 842 行/196,013,728.80；合并数据从 5,526 条业务行增至 6,343 条。
- 新增清单旧版 998 行/556,193,229.24，新版 983 行/236,705,749.54，也主要受上述期初 Sheet 口径变化影响；不应以此样例直接判定净增额逻辑有误。
- 公式数量方面，Rust 为 5,499 行 FA List 全量写入 8 列折旧测算公式（43,992 个），旧版只有 80 个；这是现有大表阈值下的有意行为，不是卡片值差异。新版数值单元格增多、文本单元格减少，是为了保持可求和类型；样式 ID 数字不可跨生成引擎直接比较，但冻结、筛选、数值/百分比格式均存在。列宽按显示内容重算，多处比旧版宽 1–4 个字符，未发现金额列低于内容宽度。
- Rust 修复：自动选表加入业务表名/期间亲和度；点分隔日期统一为 ISO；本年折旧、新增方式、新增日期仅在文件2映射和 LLM 复核中生效。真实期初样例回归已确认重新选中 `固定资产明细 241231` 且读取 5,449 行。

## 经真实样例核对后有意偏离旧版的口径

以下三处 Rust 与旧 Python 输出**不同且不应对齐**——旧版在真实样例上被证明有缺陷。改动前请先读这一节。

| 项 | 旧版行为 | Rust 行为 | 依据 |
|---|---|---|---|
| 新增清单收录范围 | 只收 `数据来源=仅文件2`，金额取期末原值全额 | 按净增额收录（含期初原值为 0 却匹配上期初卡片的行） | 旧版明细合计比自己的变动汇总表少 615 万；Rust 现为分毫勾稽 |

## 2026-08-22 类别映射错配加固：首次复核即纠正（不再依赖 LLM 运气）

### 问题现象

真实样例（期初 2024 卡片 / 期末 2025 卡片）上，脚本把期末「资产类别」映射到列名相近的「资产分类」（实际为编码类取值），首次点击「读取表格 + LLM 复核」未纠正，第二次点击「LLM 重新复核」才纠正。

### 根因（三者叠加）

1. `fa.review` 的 system prompt 只强制逐项检查 `unmappedRoles`（未映射角色）；**已映射**角色的核对是软性的——模型可以仅凭列名相似（「资产分类」≈「资产类别」）判 keep，不核对样例数据形态。
2. payload 只有 `unmappedCandidates`（未映射角色的本地候选），没有「已映射但疑似错配」的本地信号。存量固定资产的类别取值跨年不变、两期类别列去重值应高度重叠，这一确定性信号此前完全没利用。
3. temperature 已固定 0，但 OpenAI 兼容服务不保证确定性，两次调用输出不同，于是呈现「第二次才纠正」的随机表现。

### 修复（均在 `src-tauri/src/fa.rs`）

- **system prompt 加硬要求**：已映射角色也必须逐项核对，不得仅凭列名相似判 keep，必须结合 `samples` 核对数据形态（类别列=少量重复的分类文本、原值/折旧/残值率=数值、日期=日期、寿命=月数），形态不符且另有更符合的列时必须返回 `action=review` 建议；并要求优先复核 `suspectMappings`。
- **本地「类别疑似错配」检测**（`local_category_mismatch_suggestions`，随 `main_llm_payload` 计算并以顶层字段 `suspectMappings` 随载荷下发）：两侧类别列去重值（前 2000 行、至多 200 个）重叠率 < 0.2 且对侧去重值 ≥ 3 个时，在本文件表头里找与对侧类别集重叠率 ≥ 0.5 的替代列（跳过当前列、匹配键列、编码列；名称列跳过但列名含 类型/类别/分类/大类 的「资产类型描述」类列除外），产出 `confidence 0.9 + action=review` 的建议，两侧对称检查。阈值保守，宁可漏报不误报。
- **`finalize_llm_review` 兜底注入**：LLM 输出（suggestions+fieldReviews）中没有指向同一 `(role, file_side)` 的项时，把 `suspectMappings` 注入 suggestions 走既有分流——0.9 的 review 项进 `fieldReviews`，前端 ≥0.6 自动应用并进变更清单（可逐条撤销），与「先改后核」口径一致。supplement 载荷无该字段，自然跳过。

### 对应测试

- `local_category_mismatch_flags_end_side_when_values_do_not_overlap`（期末错配→产出 file2 建议，替代列取「资产类型描述」）
- `local_category_mismatch_keeps_quiet_when_categories_overlap`（正常重叠→不产出）
- `local_category_mismatch_requires_enough_distinct_categories`（基准去重值 <3→不产出）
- `finalize_injects_local_suspect_mapping_when_llm_missed_it`（LLM 漏报→兜底进 fieldReviews）
- `finalize_does_not_duplicate_suspect_mapping_llm_already_returned`（LLM 已报→不重复注入）

### 尚未验证

- 仅合成样例；真实两期卡片上「资产分类=编码、资产类型描述=类别文本」的原始文件未入库回归，结论待脱敏样例验收。
- 替代列排除规则对「类别列同时长得像名称列」的其他命名变体（如「资产类别说明」）覆盖面未逐一验证。

### 2026-08-30 科目自动分类改按科目层级判定，报告期间空跑改为报错

一份真实客户账（`汇兑损益测试资料/科目余额表.xls` ＋ `序时账-1.xlsx`，210/169 个科目、7311 行 JE）

- **科目角色只按名称关键词判**，`16020002 机械设备` 挂在 1602 累计折旧下面却被判成原值；
  `5301000125 直接投入-仪器设备维护费`、`5301000128 直接投入-房屋租赁费` 也被"设备""房屋"二字捞进原值。

  上级科目的结论一路继承给下级。真实样例上 13 个固定资产科目全部判对，1604 在建工程、1606 固定资产清理、
  5301 研发支出整枝排除。判定在前端 `suggestFaAccounts`（引擎只收前端确认后的 `accountAssignments`）。

- 科目复核默认只显示固定资产候选 → 改为默认列全部科目，原值/折旧在前、其余科目标记「排除」垫底；

#### 第二套真实账（4800，SAP 型科目表）暴露的三处续修

`TB-4800.xlsx` ＋ `4800_JE_2025.01-12.xlsx` 导出时报了 12 条「有累计折旧变动 … 无法归属到原值类别」。
逐条查下来全部是误报，根因是**科目串里的编码没被认出来**，牵出三处：

- **科目编码可能拼在串尾**。科目串由映射到的科目列按列序拼成，这套余额表的列序是
  「科目名称一级 科目名称二级 科目代码」，编码落在最后（`固定资产 固定资产-累计折旧-计算机及硬件设备 1601140001`）。
  原先只认串首编码，认不出就把编码当成名称的一部分带进资产类别——原值那侧类别成了
  `计算机及硬件设备 1601040001`、折旧那侧成了 `计算机及硬件设备 1601140001`，两边永远配不上对。
- **累计折旧不一定挂在 1602**。这套科目表把累计折旧放在 1601 的子科目里（`1601130001` 等）。
  判定改成两层：编码定「在不在本表口径内」，科目名称写了「累计折旧」就定折旧，
  这样国标表（1602 整支）与 SAP 表（名称为准）都对。名称写「减值准备」「清理」「折旧费」「摊销」「租赁费」的一律排除。
- **损益类科目按编码整片排除**。`6601090401 折旧费-固定资产-计算机及硬件设备`、`6601330001 设备租赁费`
  名称里带「固定资产」「设备」，只看名称必然被当成原值捞进来。数字编码不以 1 打头的一律排除
  （1 资产／2 负债／3 共同／4 权益／5 成本／6 损益）；字母开头的自定义编码不适用，继续按名称判。

另外，同一科目在 TB 与 JE 里会拼出两种科目串（列序不同、名称取的列也不同），两条分类都要保留
（各自参与一侧匹配），但**角色与资产类别按科目编码归一**：角色用信息最全的那个名称判，
类别取首次出现的（科目串 TB 在前 JE 在后，等于以余额表科目名为准）。不归一的话，同一科目的两条分类
会带着不同类别送进引擎，轻则原值与折旧配不上对，重则直接触发 `FA_TBJE_ACCOUNT_ASSIGNMENT_CONFLICT`。
科目复核界面里改一行也会同步到同编码的其他行，避免用户只改一半。

4800 复核结果：警告 0 条，三个类别的原值／折旧全部配上——办公设备（已提足）、
机器设备（3286252.87 → 3179252.87，107000 全额计提资产处置）、
计算机及硬件设备（本年计提 7694.44 = 10×769.44＋0.03）。

**「无法归属到原值类别」本身不是噪声**：它表示某个累计折旧科目的资产类别在 TB 里找不到同名的原值科目。
第一套账修完后仍留 3 条，全部指向 `16020002 累计折旧-机械设备`（期初 425082.62、期末 0，而 1601 下没有机械设备原值），
这是真实的账务情况，需要人工判断，不该被消掉。
