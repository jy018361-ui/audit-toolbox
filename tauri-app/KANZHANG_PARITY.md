# 看账小工具迁移功能矩阵

## 2026-09-06 · 自动标题行复用文件指纹缓存

- 51.2 MB 的 `04JE.XLSX` 实测中，Parquet 数据缓存命中后读取 164,420 行 × 61 列只需约 4.8 秒，但自动标题行识别仍会通过 calamine 解压整张工作表，总等待约 55.6 秒。OOXML 首次识别现复用汇兑引擎的 zip 前缀读取，只流式解压工作表前 32 行；识别结论再按规范路径、文件大小、修改时间及 Sheet 选择持久化。同一文件再次读取直接复用，源文件或 Sheet 改变时自动失效。
- `.header` 记事文件与 `.sheet` / Parquet 缓存共用统计、手动清理及周期清理。显式标题行不读写该缓存，大 CSV 仍固定按第 1 行处理。
- 回归：`cargo test --manifest-path src-tauri/Cargo.toml --lib auto_header_row_memo_is_reused`；真实 `04JE.XLSX` 通过 worker 的标题缓存冷、热两次读取对照。

## 2026-09-06 · 导出金额校验接入公共正文判定，表尾小计/公式残值行不再拦截

- 起因是 TBJEPBC 10 号序时账实测：正文后面留着两行手工核对公式（SUBTOTAL 小计行、引用外部 FA list 失效后缓存值变 `#REF!` 的核对行），都没有凭证号与科目。看账导出前的金额门禁对**原始全表**跑，`#REF!` 在正文过滤生效之前就把导出拦下——其余工具（借款/存款/汇兑/FA勾稽/TBJE）早已接入 `ledger_junk_mask` 正文判定，唯独看账没接。
- 修复口径与借款利息同序：`preprocess_ledger` 先按公共引擎剔非正文行（表尾小计/手工草稿、有钱没身份的游离行），**再**做非金额列向下填充——填充会把上一行的科目/凭证号带给空白格，垃圾行被填上身份后就再也认不出来、还会混进发生额。金额校验同样只对正文行报错；真实分录行（有凭证号/科目、至少一个金额列可解析）的坏值照拦。
- 大 CSV 流式路径拿不到全表视野（表尾倒扫做不了），改用引擎新抽出的单行判定 `LedgerBodyRule`（业务行协议＋游离金额行两条判据），非正文行不校验、不填充、不进正文；表尾噪声靠业务行协议兜底。
- 报错可定位：五处金额门禁（看账内存/磁盘、汇兑、借款、TBJE）的主文案统一折进首处位置（列名＋行号＋原值，80 字截断），与看账磁盘路径既有措辞一致——job 失败事件只回传 `user_message`，位置留在 detail 里用户永远看不到。
- **行为变化**：此前看账会把表尾小计行借向下填充计入导出正文；单金额列整列坏值的行此前以 0 进正文、现在按非正文行剔除（与借款/汇兑同一语义）。
- 回归：`cargo test --manifest-path src-tauri/Cargo.toml --lib`（新增 `表尾小计与失效公式行不拦导出也不进正文`、`正文行的坏金额照拦且指明行列位置`；既有 `看账公共入口拦截金额列非数值` 仍拦真实行）。

## 2026-09-04 · 大 CSV 低内存完整凭证分析与动态资源保护

- 2026-09-06 补充：正负数标记的大文件路径与普通路径统一了跨凭证排序、金额＋方向模式禁用跨凭证匹配、主体首尾空格处理；中途取消或失败会清理 `.partial`。用户选择非 CSV 明细输出时明确提示改选 CSV，不再静默改后缀。
- 预览漏斗的任意列取值使用 SQLite 去重索引，返回值排序、关键字、`total` 和 `truncated` 与内存路径一致；金额口径报告直接读取公共 prepared 证据，不再因 6GB 文件尝试整表载入。

- 纵向合并 CSV 中间可能保留后续来源文件的重复表头；磁盘缓存访问层会识别并跳过这些结构行，已有缓存无需重建。科目索引使用新版表名重新生成，避免重复表头污染科目列表；真正的金额脏值仍会报出列名、行号和值。
- CSV/TXT/TSV 是否进入独立 SQLite 行缓存改由动态预算决定：不超过 64 MiB 时用保守六倍放大快速判断且不额外采样；64 MiB～2 GiB 读取开头最多 16 MiB，按行数、分隔符数量和预处理工作系数估算峰值，超过当前 worker 预算 65% 时走磁盘；达到 2 GiB 时无条件走磁盘。流式解码继续保留标题行、原始字符串/前导零、引号内换行、行顺序及宽度补齐。安全余量充足的普通文件继续使用原内存/Parquet 路径，并去除 CSV 整理及列转换的多余字符串复制。
- 大文件缓存按源路径、大小、mtime、标题行隔离；逐行写入，事务完成后原子发布。科目唯一值及首个编码/一级名称在磁盘上索引，不把全量明细读回；查询复用映射专属索引。SQLite 缓存纳入既有缓存统计与清理。
- 读取时显示已缓存行数、检查真实取消信号；单条 CSV 记录采用字节预算，超长记录安全失败；创建缓存前检查磁盘空间。
- 首次科目汇总同样走可取消任务通道，按已扫描行数显示百分比；科目索引仅以科目列映射为键，第一步生成后进入第二步直接复用，并兼容迁移 alpha.49/50 已生成的索引。界面称为“磁盘分批模式”，避免把固定磁盘路径误解为固定内存额度，实际内存上限和批量仍由主机状态动态决定。
- 看账后台任务发送读取请求前安装 Windows Job Object 内存限制。预算根据主机总内存、当前可用内存和提交余量动态计算；空闲内存偏低时保留约 10% 物理内存作为启动安全底线，worker 只使用剩余安全余量的一半，并同步缩小批量与 SQLite 缓存，以较长处理时间换取可运行性。启动前余量不足时任务留在队列自动等待；运行中跌破动态暂停线后停在最近的分批检查点，内存达到两倍暂停线并稳定 5 秒后自动继续，也可手动触发安全重试。只有跌破更低的危险线并持续 15 秒才终止；用户主动暂停仍只由用户继续。8/16/24/32/64 GiB、16 GiB 主机仅剩 3 GiB，以及暂停/恢复/危险三区间由纯函数回归覆盖。2 GiB 以上的文本账表固定走磁盘路径，不会因电脑内存较大而改回整表加载；中型文件随实时预算选择路径。正常文件不主动限制线程。
- 大 CSV 已接入磁盘凭证索引：按多列凭证 ID 和公司隔离凭证，前向填充映射字段，先命中目标科目再扩展整张凭证。多个目标批次分别筛选，可流式写出明细 CSV 分片及剔除明细。
- 合并来源允许省略行尾空字段：磁盘缓存继续保留各行原始宽度，流式导出时按最宽表头补齐尾部空列，避免同一文件中 116/117/118 列记录混合时被 CSV 写入器误判为失败；单行补齐后立即写盘，不增加整表内存占用。
- 凭证分析索引改为按“源文件指纹 + 字段映射 + 金额方向口径 + 算法版本”持久缓存。首次筛选/导出完成后，下一步骤、重试导出和再次打开同一文件会直接复用，不再重复扫描全表、创建四类索引和校验借贷平衡；源文件或映射变化会生成独立缓存。分析库只保存原始缓存行号及筛选字段，明细内容按行号回查原始行缓存，不再复制一份整行 JSON。批次金额方向保存在当前任务状态中，不再对分析库做整批 `UPDATE`。
- 大文件导出的进度按“打开缓存、整理明细、创建四类 SQLite 索引、识别金额方向、借贷平衡校验、批次筛选、套表分析与明细写出”加权到统一的 0–1000 区间。扫描行缓存只占整体前半段，四类索引逐项提示，完成事件前不会显示 100%。
- 套表分析在 SQLite 中分批汇总并以恒定内存写出 XLSX，支持凭证、宽松/严格凭证类型、透视分析、科目汇总、隐藏目标清单和可选 LLM 分析；损益结转按完整凭证识别并排除类型及自定义透视分析。分类最小集合、透视列集合和单条记录受动态预算保护，超限时提示缩小目标科目批次或减少透视列，明细筛选仍可单独使用。
- **剩余限制**：第一次使用一种新映射仍必须完整扫描一次并建立持久分析索引；缓存命中只能消除后续重复工作。大文件明细只接受 CSV 分片输出，套表另存 XLSX；直接要求 XLSX 明细会被拦截。Excel 套表仍受 1,048,576 行和 16,384 列上限约束。动态磁盘路径仅适用于 CSV/TXT/TSV，XLSX/Parquet 尚未改为流式导入。公共 SQLite 行访问接口已供汇兑损益复用：上传识别只取有限样本，正式任务从同一磁盘缓存投影已映射字段；FX 当前仍需把投影后的计算字段装入受限 worker，投影本身仍超预算时会保留缓存并安全退出，尚未完成完全基于磁盘的凭证聚合。磁盘套表的数据页已接入，但暂不宣称隐藏 `_targets` 内部列结构、列宽、合并单元格及条件格式等版式细节与普通路径完全一致。
- 回归：`cargo test --lib -j 1 --manifest-path src-tauri/Cargo.toml tabular:: -- --test-threads=1`；`cargo test --manifest-path src-tauri/Cargo.toml resource_budget::tests::adaptive_ -- --test-threads=1`；`npm run build`；`npx vitest run src/KanzhangParityPage.test.ts src/components/JobDialog.test.tsx --exclude .claude/**`。真实 worker 的受限诊断使用 `scripts/diagnose_kanzhang_import.py`；普通/磁盘路径的合成业务对照使用 `scripts/verify_kanzhang_disk.py`，范围与门槛见 `KANZHANG_LARGE_FILE_ACCEPTANCE.md`。
- 已完成的本机实测仍只覆盖导入：6.41 GB CSV（9,640,502 行、118 列）完整读取及科目索引约 814 秒，0.2 秒间隔采样峰值私有内存约 12.81 MiB；再次读取约 0.24 秒。16.6 MB 普通文件对照的预览、映射和科目结果一致，单次内部读取耗时 1553 ms → 1248 ms。尚未用这份真实 6.41 GB 文件完成筛选与套表导出，因此不能把合成回归写成真实大文件完整验收，也不代表所有文件提速。

## 科目字段：编码与名称已拆成两个角色（2026-08-24）

此前界面上只有一个可多选的「科目名称」槽，编码列（`会计科目`、`科目代码`）和名称列
（`科目文本`）都落在里面，下拉里根本选不到「科目编码」——统一映射内核明明分得出这两个
角色，是看账取结果时把它们合并了。现在两个角色各自独立：

- **必填口径变了**：不再要求「科目名称」，改为**编码与名称至少映射一列**
  （`missingKanzhangRequiredRoles` / `validate_kanzhang_mapping` 同口径）。
- **科目键不变**：`account_columns()` 按**编码在前、名称在后**拼接，与拆分前
  `suggest_mapping` 产出的列顺序一致，已有的目标科目选择不会因此对不上。
- **旧参数仍可读**：`LedgerMapping` 保留 `account` 字段做反序列化兼容，老草稿、
  老任务参数拼出的科目键与拆分前相同；前端草稿缓存键升到 `v3`。
- **LLM 复核**：提示词改用 `accountCode` / `accountName`，模型沿用旧名 `account`
  时前端归到科目编码；另新增一道冲突词过滤（`role_rejects_header`），模型把
  `预算二级科目描述` 这类列指给科目名称的建议会在应用前被丢弃。

拆分只动角色划分与界面，不改导出口径——下游一切按 `account_columns()` 拼出的科目值走。

## 2026-08-08 凭证类型归类算法移植

把 Rust 侧的一次性哈希分组换成旧版的**两阶段并查集归并**（`classify_vouchers`），
`build_voucher_type_rows` 的标签编号、摘要取数、月份列、行排序也一并按旧版重排。

### 移植了什么

| 旧版语义 | 位置 |
|---|---|
| 只有净额四舍五入到分后仍非零的科目才进「科目集合」并计方向 | `voucher_infos` |
| 「基准集合」= 现有凭证科目集合中的最小集合；一张凭证挂到「元素最多、同数量按字典序最小」的那个子集上 | `minimal_account_sets` / `order_base_sets` / `pick_base_set` |
| 只比较**共同出现**的目标科目方向；额外目标科目不阻止归类，但会并进组的方向表 | `compatible_signs` / `attach_to_base_group` |
| **恰好一个基准组兼容才合并**：零个（无基准）和两个以上（有歧义）都让凭证单独成一类 | `attach_to_base_group` |
| 宽松：先按目标科目集合归并，再对「找得到目标基准集合」的凭证按全科目集合归并一次 | `classify_vouchers`（loose 分支） |
| 严格：按同一凭证的目标科目个数分流（>1 走目标集合、=1 走全科目集合），种子只能由「集合恰好等于最小集合」的凭证担任，最后对单目标凭证按全科目集合做一次兜底合并 | `classify_vouchers`（strict 分支） |
| 「类型 N」按**代表凭证号排序后的名次**编号，与遍历顺序无关 | `build_voucher_type_rows` |
| 行序：先按（类型标签、科目名称）升序，再按「标签里第一个科目名 + 最后一个类型编号」稳定倒序 | `type_sort_key` |
| 净额与所有月份都为 0 的科目行不展示 | `build_voucher_type_rows` |

顺带修掉两处旧实现的副作用：净额为 0 的科目此前会被整行丢掉（现在只在月份也全为 0 时才丢），
以及 `-0.0` 会被格式化成 `"-0"`（`round_to_cent`）。

### 真实样例验收（JE-用于测试 / JE-PRC，36,340 行明细，62 个目标科目）

| | 旧版导出 20260805 | 本次新版 | 类型指纹（科目+净额）差异 |
|---|---|---|---|
| 凭证类型-宽松 | 63 类型 / 566 行 | **63 类型 / 566 行** | 双向都是 0 |
| 凭证类型-严格 | 277 类型 / 1,797 行 | 296 类型 / 1,854 行 | 只在旧版 2 个 / 只在新版 21 个 |

宽松表已经**完全对上**：类型数、每个类型覆盖的科目与净额逐项一致（此前是 567 ↔ 894 行）。

### 为什么严格表还差一截，以及为什么「代表凭证」注定对不齐

旧版遍历凭证的顺序来自 `polars.group_by()` 的哈希顺序，而这个算法是顺序敏感的——
谁先出现谁就当基准组的种子，后来的凭证只有「恰好一个组兼容」才归队。
用同一份数据、同一份 `kanzhang_app.py` 直接跑两次，严格表就会得到 **277 类型 / 1,797 行**
和 **286 类型 / 1,833 行**两种结果，代表凭证与「类型 N」也各不相同。
也就是说**旧版自己就不可复现**，逐行对齐某一次导出没有意义。

新版把遍历顺序固定成「凭证在底稿里第一次出现的先后」（`voucher_infos` 保留出现序，
不再用凭证号字典序），这是确定性的，也是唯一能解释给复核人听的口径：
代表凭证 = 该类型里最先出现的那张凭证。宽松表在这个顺序下与旧版完全一致；
严格表 296 类型落在旧版自身 277–286 的波动区间外侧约一成。
全部差异只落在两簇凭证上——`管理费用_水电暖费_电费` 和 `管理费用_劳动保护费`，
形态都是「只命中一个目标科目、全科目集合同为 {进项税额, 该费用, 银行存款}、但费用方向一正一负」。
这类凭证的基准组种子是哪个方向，决定了另一个方向的凭证是并进来还是各自成类；
种子取自遍历顺序，所以旧版每跑一次结果都可能不同。

- **套表页签顺序**：旧版是 凭证 → 凭证类型-宽松 → 凭证类型-严格 → 透视分析 → `_targets` → LLM分析；

- **透视值字段选不到净额**：净额是按金额方案算出来的伪列，不在源表列里，
  界面的下拉只列源表列，于是"留空=净额"成了唯一入口，想同时看净额和某个原始金额列做不到。
  下拉已补上「净额」这一项，后端也不再在显式选中时把它丢掉。

### 剩下的差异，以及为什么不再追

**归类算法本身已确认是忠实移植。** 用 `scripts/kanzhang_parity/legacy_voucher_type.py`
按「首次出现序」跑这份底稿，得到宽松 39 类型 / 504 行、严格 277 类型 / 2,251 行，
与新版 Rust 输出**逐行逐格完全一致**（两组真实底稿都通过 `kanzhang_voucher_type_matches_legacy_sample`）。

**旧版自己跑两次结果就不一样。** 把 `kanzhang_app.py` 拉出来对同一份数据重跑：

| | 旧版导出 20260808 | 旧版重跑 | 新版 |
|---|---|---|---|
| 宽松 | 39 类型 / 486 行 | 39 类型 / 486 行（指纹一致，但代表凭证与「类型 N」全不同） | 39 类型 / 504 行 |
| 严格 | 279 类型 / 2,258 行 | **280 类型 / 2,261 行** | 277 类型 / 2,251 行 |

严格表连类型数都对不上，宽松表虽然分组稳定但代表凭证换了一批——
根因还是遍历顺序取自 `polars.group_by()` 的哈希顺序。新版固定用「首次出现序」，
是这三者里唯一可复现、也唯一能向复核人解释的口径。

### 一处有意不对齐（新增）

- **整行为 0 的科目行**：旧版判断"这行要不要展示"是拿未取整的浮点和比 0，
  于是净额 `5.9e-12`、月份全 0 的行会被留下来，表上显示成一整行 0。
  这点残差取决于求和顺序，换个实现就不一样。新版改成净额与每个月份都四舍五入到分之后再判断，
  整行都是 0 才丢——第一组严格表的 2,252 → 2,251 就是这一行。
  净额为 0 但月份有正负对冲的行仍然保留（已有单测覆盖）。

## 2026-08-09 科目筛选拖拽

**现象**：三个穿梭区早就写了 HTML5 拖放（`draggable` + `dragover`/`drop`），条目也拖得动，
但松手永远落不下去，用起来就是"不支持拖拽"。

**根因不在页面代码**：Tauri 在 Windows 上默认开着窗口级的文件拖放（`dragDropEnabled`，
配置里没写就是 `true`）。这个开关一开，WebView2 会把页面内的 `dragover`/`drop` 整个吞掉——
官方文档也写明"要在前端用 HTML5 拖放，必须关掉它"。
但关掉它会连累别的页面：`App.tsx` 和 `ConfirmationProgressPage.tsx` 靠
`tauri://drag-drop` 事件接"把文件拖进窗口"，而 HTML5 的 `File` 对象拿不到本地绝对路径，替代不了。

**做法**：科目穿梭区改用 Pointer Events 自己实现拖拽，不再依赖 HTML5 拖放，两边都不牺牲。

- 按下后把阈值判定挂到 `window` 上（不是条目自身的 `pointermove`），
  光标甩得再快也不会因为离开条目边界而收不到事件；移动超过 5px 才算拖拽，普通点击照旧选中。
- 落点用 `document.elementFromPoint` + `closest("[data-shuttle-zone]")` 判定，
  拖到空白处或窗口外一律不产生移动；按 Esc 取消。
- 拖影自己画（`.kz-drag-ghost`，`pointer-events:none`），单选显示科目名，多选显示"N 个科目"。
- **自动滚屏**：待选区和目标区在窗口里是上下排的，一屏装不下（1440×900 下目标区在 y≈1200）。
  浏览器只给原生拖放自动滚屏，所以光标贴近视口上下边缘时自己滚：先滚光标所在的列表，
  滚不动了再滚页面。没有这一条，用户根本拖不到目标区——这多半也是"拖拽没用"的一部分体感。

**验证**（vite dev + 浏览器实测，非仅靠推理）：单击选中、Ctrl 加选后整批拖动、
从目标区拖回待选、拖到空白处不动、贴边自动滚屏后成功落入目标区，逐项确认通过。
