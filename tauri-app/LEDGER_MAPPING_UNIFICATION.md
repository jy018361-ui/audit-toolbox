## 0.3 主体降为选填，映射面板改按型号组织（2026-08-29）

两处都是「设计早就定了、界面没跟上」的落差，起因是一轮当面复核。

**一、`entity` 是选填，界面却当必填拦。**
金标 2026-08-24 就把主体从 required 降为可选（`identity_required` 里没有它），
但汇兑损益前端把「公司/核算主体（或固定主体）」列进缺失清单、后端另有两条
「缺少主体列时必须指定固定主体」的阻断，FA TBJE 还要用户在识别步骤手填主体名。
三处全部拆除，改为：

| | 做法 |
|---|---|
| 没映射主体列 | 全表统一挂 `DEFAULT_ENTITY`（「默认主体」），不提示不阻断。Rust `fx::fixed_entity` 与前端 `ledgerMapping.DEFAULT_ENTITY` 同一个名字 |
| 映射了主体列 | 按列里的主体走，与原来一致；汇兑损益单主体时沿用该主体名做底稿封面 |
| 界面 | 汇兑损益那两个格子（固定主体名 ＋ 本位币）收敛成一个「本位币（全表）」——**真正必填的一直是本位币**，主体只是它的挂载点；FA TBJE 的输入框保留但改为选填，留空按默认主体 |

**二、下拉分组按字段类别切，看不出「这几个格子为什么突然必填」。**
分组标题此前写死「本位币金额　必填，三种记法选一种」，与当前命中哪一型无关。
现在改为按**当前命中的型**组织，五个工具共用：

- 新增 `ledger.forms` 下发 TB 六型／JE 三型的槽位定义（台账那份仍随 `loan.inspect` 下发），
  前端 `src/ledgerForms.ts` 只做纯计算，与 Rust `match_forms` 同一套排序规则与次选口径
- 面板顶部给一句结论：「已识别为 TB-类型C（本位币借贷分列）」／「最接近 …：缺少「本年累计借方发生额」」
- 分组顺序：身份类 → 这一型的各槽位 → 本期发生额（次选口径）→ 其他记法（这一型用不到，但仍可选）
- 必填标记逐项跟着型走（`＊`／`（选填）`），借款台账早就是这么做的，这次把 TB/JE 接上

**型号名一律用字母**：`Form` 新增 `display` 字段，`TB1..TB6` → `TB-类型A..F`、
`JE1..JE3` → `JE-类型A..C`、台账 `A..D` → `台账-类型A..D`。
**`id` 保持不变**——代码、测试与金标的那两张类型表都在用它，改了对不上。

**三、顺带修掉一个表头回归。** 同期新加的「两行表头作为一个候选整体参与竞争」
（`fx::infer_header_layout`，为的是别让 `借方/贷方` 那一行单独胜出）没有区分
**分组表头**与**标题行**：`序时账` 这种只有一格有字的标题行也会被并进表头，
`merge_headers` 把它顺延到每一列，列名全变成「序时账-公司代码」。
后果有两个——映射标签被污染，以及汇兑/存款读到合并表头、看账那侧仍按单行读，
两边表头对不上（`ledger_engine_parity_tests` 因此转红）。
现要求**上一行至少两格有字**才作为分组表头参与配对，标题行照旧跳过。

回归：`npx vitest run src/ledgerForms.test.ts src/FxAuditPage.test.ts src/FaTbJePage.test.ts`；
`cargo test --manifest-path src-tauri/Cargo.toml --lib`。

## 0.1 第二轮：按金标对齐（2026-08-24）

`汇兑损益测试资料/TB-4800.xlsx` 里有两个此前没被用上的工作表——`tb种类`（六型）与
`je种类`（三型），逐格标注了每个角色是 required 还是 optional、哪个可多列。
**这两张表提升为账表类型定义的正式来源**，与内核逐格比对后做了四处改动：

| 改动 | 说明 |
|---|---|
| 收编三个游离角色 | `auxiliary` 辅助核算（可多列）、`loanId` 借款明细、`period` 会计期间（仅 TB）。此前汇兑损益靠一行 `role == "auxiliary"` 特判、借款利息按关键词临时找，都已拆除 |
| 必填改为并集 | `missing_required` 现在返回 **金标身份槽 ∪ 金额形态槽 ∪ 工具自己声明**，每条带 `from_gold` 标明是谁在要求。前端 `missingGoldIdentity` 是同一份定义 |
| JE 形态优先级修正 | 排序规则是「同为完整命中时后定义的型优先」，而 JE 数组原本正序排列，导致纯净额型排在方向型前面。数组倒置后 4800/3300 两份序时账正确判为 JE2 |
| 本期发生额作次选口径 | 金标只写了本年累计，但实测「科目余额表.xls」（用友）只给本期发生借贷。本年累计缺失而本期借贷齐全时放行，与汇兑损益前端既有的「本年累计（或本期）」口径一致 |

**`auxiliary` 的别名只收汇兑损益那一份**：存款利息另有一份把「文本／科目文本／账户文本」
也算辅助核算（它靠这些列认存款档次），并进标准表会把科目名称抢走。工具需要额外写法时
在自己那边追加，标准表保持保守。`loanId` 同理只认「合同编号／借款编号／借据」这类特异写法，
`辅助`、`明细`、`客户` 这类泛词留给 `auxiliary`。

**这是一次实质收紧**：金标要求 JE 的记账日期、凭证识别字段、科目编码、科目名称、摘要齐备，
TB 要求科目编码与名称齐备——缺一项就拦。今天能跑的账里，缺摘要列的、只有科目编码没有名称的，
改造后都会被拦下。`entity` 不在其中（金标 2026-08-24 修订时降为可选），汇兑损益仍自己要求它。

| 层 | 做法 |

### 币种一律分两列（2026-08-25）

金标的两张类型表这天补齐为 `原币currency` ＋ `本位币currency`——TB 本来就分两列，
JE 那栏此前只写了一个 `currency`。核对代码后确认**内核一直是分两列的**
（JE 与 TB 都有 `currency` ＋ `functionalCurrency`，汇兑损益也逐行在读本位币币种列），
但有两处没跟上：

| 问题 | 说明 |
|---|---|
| **JE 面板选不到本位币币种** | `JE_LABELS` 里没有 `functionalCurrency`，映射面板的「币种」组只列了一项。后端认得、界面给不了——序时账上用户根本没法指定本位币币种列，只有科目余额表能选。已补 |
| **同一角色两套中文标签** | `currency` 在 JE 叫「交易币种」、在 TB 叫「原币币种」。已统一为「原币币种」 |

这类三位代码，原来的叫法容易和「本位币金额」混淆。LLM 的 JE 币种段也按两列重写，

### LLM 复核实测（2026-08-25）

对 `汇兑损益测试资料` 逐份跑真实复核（跳过三份几十万行的大文件，表头映射用不到它们）。
第一轮跑出两条错误建议，都不是模型"笨"，而是**我们没把该给的信息给它**：

**一、没告诉模型脚本已经判出什么形态。**
`序时账-1.xlsx` 既有账里导出的原始「金额」列，也有客户用 `=IF(方向="借",金额,-金额)`
算出来的「借正贷负」列。模型看到金额列全是正数，就以 0.95 的置信建议改指过去。
它不知道脚本已经判定 **JE2（方向＋净额）完整成立**，更不知道在 JE2 下净额列
有没有正负号根本不影响结果——**符号口径由数据配平判定，不由列名判定**。

送给模型的 payload 里只有表头、样例和当前映射，**没有形态结论**。现在补上
`currentForm`（型号 id、标签、是否完整命中、缺哪些槽），并在通用纪律里写死：
complete 为 true 时构成该形态的槽位一律不要动，**两种映射都能成立时维持现状**。

**二、集团货币的排除对序时账从来没生效过。** 这是个既存缺陷。
模型建议把本年累计贷方指到 `MTD Grp Curr`，理由里自己都写着「为集团货币口径」。
查下去发现两个洞：

- 判断"是不是金额角色"用的是 `contains("Functional")`，**大小写敏感**。角色名有
  `functionalAmount`（小写开头）与 `ytdFunctionalCredit`（驼峰中段）两种写法，
  **JE 的三个金额角色一个都匹配不到**。一份只给集团货币金额、不给本位币金额的
  序时账，会把集团货币当本位币收下。已抽成 `excludes_group_currency` 并改为大小写不敏感。
- 排除词表里有 `groupcurr`，但 SAP 实际写的是 `Grp Curr`（`MTD Grp Curr`、
  `YTD Act (Grp Curr)`），匹配不到。已补 `grpcurr` / `grpcurrency`。

两处修完重跑：**五份样例全部「无修改建议」**，脚本的形态判定一个没变。

> 一度加过一条"列名带 `借正贷负`／`唯一码` 就拦"的黑名单规则。**已撤除**——
> 那是对着症状打补丁，把信息给足之后模型自己就不提了。留着反而会误伤
> 那些净额列本来就叫「借正贷负」的账。

**回归测试**：9 家公司的真实科目余额表与序时账（用友／金蝶／SAP／Oracle EBS，含繁体、
段式科目、双语表头）共 18 份表头固化在 `ledger_mapping.rs` 的 `TB_FIXTURES` / `JE_FIXTURES` 里，
逐列比对期望角色。新收到一种形态就往里加一条。

**多列同名时按金额量级消歧**：一张余额表同时给「本期发生」和「本年累计」两组、
却都只写「借方发生额」的情况很常见，列名分不出来。本年累计覆盖的期间更长，合计一定不小于本期，
抽查若干行比大小即可（`MAGNITUDE_SAMPLE_ROWS` 行内至少 `MAGNITUDE_MIN_VALUES` 个有效数值才下结论，
量级持平就维持别名判定）。**集团货币／报告货币是第三套口径，整体排除在金额角色之外**——
SAP 那份 TB 的集团货币数字大出七倍，拿它跟本位币比量级会把本年累计判到错的那一列。

**方向列不是独立必填**：它只在某一型内部与净额成组出现。没有方向列时命中「净额」型（TB1／TB4），
有方向列才命中「方向＋净额」型（TB2／TB5），两种都不报错。序时账同理——借贷分列本身已表达方向，
JE1 不要求方向列。

**两处按真实数据改掉的设计**：

1. **JE1 不再要求方向列**——9 份序时账里借贷分列的有 6 份，没有一份带方向列。
   借贷分列本身已表达方向，有方向列时只作校验。
2. **没写「本期／本年」的发生额一律按本年累计**——实务表大多直接写「借方发生额」，
   审计导出的是全年数。只有明确写了「本期」的才落本期口径。

## 1. 为什么要做

五个工具都要让用户把 Excel 表头对应到业务字段，做的是同一件事，代码却有四套。

| 工具 | 读表 | 候选打分 | 角色定义 | 校验 | LLM 复核 | 前端界面 |
|---|---|---|---|---|---|---|
| 汇兑损益 | 自有（含大文件轻量路径） | 完整 | JE 17 ＋ TB 21 | 完整 | 有 | `FxPreview` |
| 存款利息 | 复用汇兑损益的 | **复制粘贴自汇兑损益** | JE 11 ＋ TB 8 | 自有 | 有 | `MappingPreview` |
| 借款利息 | 自有简化版 | 无打分 | 简化 | 只查必填 | 无 | `Mapping` |
| 看账 / 正负数 | 用 `tabular` 的 | 自有 | 固定 9 字段的 struct | 自有 | 有 | `LedgerMappingPreview` |

代价已经付过一次了。这次修汇兑损益时解决的三个问题，另外四个工具原封不动地还在：

1. **科目编码和科目名称混在一个字段里**——存款、借款、看账都还是一个叫"科目编码/名称"的格子；
2. **币种列整列同值时被误当成交易币种**——存款利息的 TB 映射同样有"币种"栏，遇到 SAP 那种整列填本位币的导出会把全表科目当外币；
3. **TB 与 JE 之间没有口径校验**——存款和借款同样是双表工具，两边科目对不对得上无人检查。

统一之后，这类问题一处修好，五个工具同时受益。

## 2. 前提：TB 和 JE 是两种表，角色分开定义

**TB（科目余额表）一行是一个科目在某时点的余额；JE（序时账）一行是一条分录。**
这是两种不同的东西，不能混成一张角色表。本方案里，角色集、必填规则、校验规则
全部按表类型独立定义；共用的只有底层机制（读表、打分、界面渲染）。

按这条线切下来的结果：

| | 内容 |
|---|---|
| **JE 专属角色** | 记账日期、凭证识别字段、凭证类型、摘要、交易币种，以及本位币与原币两套发生额（净额／方向／借方／贷方）。见 §3.2 |
| **TB 专属角色** | 原币币种、币种线索文本、本位币列，以及期初余额、期末余额、本年累计发生额、本期发生额，各有本位币与原币两个口径。见 §3.3 |
| **两表共用角色** | **只有 3 个**：`entity` `accountCode` `accountName` |

这 3 个共用角色**全部是科目身份字段**，没有一个是金额字段，也没有币种。由此得到一条明确的边界：

> **TB 与 JE 的口径对齐，只可能发生在这 3 个字段上；金额与币种永远不跨表比对。**

跨表校验的作用域因此是确定的，不需要逐工具去想"该核哪些字段"。
其中 `entity` 只作分组维度，真正做取值比对的只有 `accountCode` 与 `accountName`。

**关于"辅助信息"槽位**：§3.5 的 TB 六型与 JE 三型末尾都留了一个"辅助信息"可选槽，
但它**不是一个通用角色**——通用 `auxiliary` 已确认删除（见 §3.8）。
这个槽位的角色名按工具而定：存款利息是存款账户与档次，借款利息是 `loanId`，
汇兑损益与看账不启用。槽位统一、语义分开。

**为什么币种不算共用**：两边虽然都叫"币种"，语义并不是一回事——
JE 的币种是**分录级**的"这笔用什么币记账"，TB 的币种是**科目级**的"这个余额是什么币"。
同一个科目在 TB 上可能只有一行 USD，在 JE 上却既有 USD 原始分录、又有本位币记账的调整分录，
两边取值集合天然就不重合。何况 TB 的币种常常根本没有独立列（藏在科目文本里、
整列写的是本位币、或者每个金额列后面跟一个币种列），拿它做跨表交集校验只会制造误报。
**两张表各自定义自己的币种角色，互不参照。**

## 3. 标准角色词汇表

命名沿用汇兑损益现有的一套——它是唯一区分原币与本位币的工具，命名最完整；
而且它刚做过改造、测试护栏最厚，改它风险最大。其余三个工具改名对齐。

### 3.1 金额类角色的命名规则

金额与余额角色的名字是三段拼接：

```
{期间前缀}{币种口径}{方向形态}

期间前缀   （无）凭证发生额 │ opening 期初 │ closing 期末
           period 本期发生 │ ytd 本年累计发生
币种口径   Functional 本位币（默认） │ Foreign 原币（仅汇兑损益启用）
方向形态   Amount 净额 │ Debit 借方 │ Credit 贷方
           （借贷方向单列成 direction，不带口径前缀，见下）

例：opening + Functional + Debit = openingFunctionalDebit（期初本位币借方余额）
```

**`period` 与 `ytd` 是两个不同的东西，必须分开。**
"本期发生"取决于客户导出时选的期间，可能只是一个月或一个季度；
"本年累计发生"才是整个年度期间。**审计要的是后者。**

| 角色 | 含义 | 测算怎么用 |
|---|---|---|
| `ytdFunctionalDebit` / `Credit` | 本年累计发生额 | **首选**。审计期间就是整年，这才是要的口径 |
| `periodFunctionalDebit` / `Credit` | 本期发生额（月／季／年，看导出口径） | 次选。只有它时才用，并提示"这可能只覆盖部分期间，请确认" |

两组都映射上时，一律取 `ytd`。
这条规则同时解决了汇兑损益代码注释里记着的那次踩坑——
SAP 的 MTD（本月）列被误当成 YTD（本年累计）用。有了明确的角色区分，
就不必再靠"借贷两列必须同时映射"这种间接防护。

**方案组**：同一个币种口径下，**借贷方向只有一个角色 `direction`，不分原币/本位币。**
一条分录的借贷方向对两个口径必然相同——不存在原币记借方、本位币记贷方的情况。
所以表里只要有一列"方向"，两个口径共用它。

三种记账形态互斥，任选其一——

| 方案 | 需要映射 | 常见来源 |
|---|---|---|
| A 净额 | `…Amount` | SAP 的"凭证金额""本位币金额"，借正贷负 |
| B 借贷分列 | `…Debit` ＋ `…Credit` | 用友／金蝶的"借方金额""贷方金额" |
| C 净额＋方向 | `…Amount` ＋ `direction` | 金额恒为正、另有一列标"借/贷" |

**原币口径与本位币口径各自独立选方案，互不牵连。**
校验时两组分别判定，所以下面这些组合都合法：

| 原币 | 本位币 | 真实场景 |
|---|---|---|
| A 净额 | A 净额 | SAP：凭证金额 ＋ 本位币金额，都是借正贷负 |
| B 借贷分列 | B 借贷分列 | 国内 ERP：原币借方/贷方 ＋ 本币借方/贷方 |
| C 净额＋方向 | B 借贷分列 | 原币只给一个正数金额，方向列两个口径共用；本位币却是借贷分列的 |
| A 净额 | B 借贷分列 | 混合导出 |

只有汇兑损益启用原币口径；其余工具只有本位币一组，不需要考虑这个组合问题。

### 3.4 币种列判定规则

TB 里的币种信息分两类，**必须分开处理，混在一起会互相干扰**：

| | 是什么 | 靠什么判 |
|---|---|---|
| **币种代码列** | 写 `USD` / `HKD` / `人民币` 的那列 | 列的取值分布，见下 |
| **金额列的口径标签** | `期初余额(原币)` / `期初餘額-本位幣` / `原币期末余额` | 列名里的"原币／本位币"字样 |

实测 9 份真实 TB：**币种代码列一律叫「币种 / 幣種 / 货币 / Ccy」，没有一份带"本位币""原币"字样**；
带这些字样的全部是金额列。所以列名规则只用于金额列，不用于币种代码列。

#### 币种代码列 → 角色

**取值先归一化**：中文名转代码（美元/美金→`USD`，港币/港元→`HKD`，欧元→`EUR`，日元→`JPY`），
`RMB` 与 `CNY` 视为同一币种；认不出的值（"外币""其他""-"、乱码）**当空处理并告警，不猜**。

**只有一列币种时：**

| 该列取值 | 角色 |
|---|---|
| 完全填满、且只有一个币种 | `functionalCurrency` 本位币列 |
| 其余一切情形（有空白，或出现两种以上） | `currency` 原币列 |

**有多列币种时：**

| 该列取值 | 角色 |
|---|---|
| 币种种类 > 1 | `currency` 原币列 |
| 只有一个币种 | `functionalCurrency` 本位币列 |

即同一条规则：**种类 > 1 就是原币列；填满且唯一才是本位币列。本位币列一定只有一个币种。**

#### 本位币的取值与反判

本位币**默认人民币**，界面上是下拉框，用户可改。已识别到 `functionalCurrency` 列时用该列的值预填；
标题行写了本位币的（实测 5 份都写了，如 `本位币 RMB`、`本位幣 Functional ccy：港元 HKD`）也用来预填。

> **反判规则**：若某列被判为 `functionalCurrency`，但它的取值 **≠ 用户选定的本位币**，
> 该列改判为 `currency` 原币列。
>
> 用途：境外主体的全美元账，币种列填满 `USD` 会被判成本位币列；用户把本位币下拉成人民币之后，
> 判定随之翻转，整表正确识别为外币账。

#### 无币种代码列时

按顺序找替代：

1. **原币金额列**有非零值 → 该科目是外币，但**币种未知**，转 2
2. **科目名称／文本**里的币种词（"美元户""（欧元）""ICBC USD"）→ 取该币种
3. 两者都没有 → 该科目是本位币科目

**纯本币账的判定**（三条全成立）：无币种代码列或其取值全等于本位币；无原币金额列或全空全零；
无任何科目名含币种词。此时**显式提示"未检出外币科目，本表不产生汇兑损益"**——
空结果表分不清是"确实没有外币"还是"识别失败"。

#### 行级取值

币种列被判为 `currency` 之后，逐行取值：

| 币种列 | 原币金额 | 科目名 | 该行判定 |
|---|---|---|---|
| 有外币代码 | — | — | 外币，按币种列 |
| 空 | — | 有币种词 | 外币，按科目名，**标记"币种列漏填"** |
| 空 | 有值 | 无 | 外币但币种未知 → 让用户指定 |
| = 本位币 | 无 | 有币种词 | 余额为零：忽略；有余额：**告警**，人工判 |
| 空 或 = 本位币 | 无 | 无 | 本位币科目 |
| 有外币代码 | — | 与之矛盾 | 按币种列，同时**告警** |

原则：**任一证据指向外币就当外币候选；证据矛盾就告警，不静默取一个。**
"币种列漏填"确有实例——同一张表里一个"美元户"填了 `USD`，另一个"美元户"币种与原币金额双双留空，
只有科目名能救，漏掉就是整笔外币借款不重估。

#### 界面上的「外币」列（2026-08-26）

上面每一条"让用户指定"，此前都没有指定的地方——只能眼睁睁看着测算把科目隔离掉。
科目分类面板（汇兑损益 → 高级设置）现在每个科目一行三列：**科目名 / 科目角色 / 外币**。

后端 `detect_account_currencies` 逐行按 `currency_for` 的同一优先级判一遍，
输出 `accountCurrencyDetails`：

| 字段 | 含义 |
|---|---|
| `detected` | 主币种（该科目出现次数最多的那个） |
| `source` | 依据来自哪里：`币种列` / `科目文本` / `本位币列` |
| `seen` | 该科目出现过的所有币种，进下拉框当候选 |
| `needsConfirmation` | `source` 是 `本位币列` 时为真——**没真识别出来** |

`source = 本位币列` 就是上表最后一行"本位币科目"的判定路径。它有两种截然不同的真相：
科目确实只有本币业务，或者**TB 那列"货币"登记的是主体本位币、科目文本里又没写币种线索**。
两者在数据上无法区分，只能交给人。实测 TB-4800 的 203 个科目里 190 个走的是这条路径，
其中 6 个（过渡银行、应付账款-关联方、其他应付款系列）JE 侧明明有 HKD／JPY 业务，
测算时因此找不到外币余额基础被隔离。

三条设计约定：

- **不预填**。下拉框留空表示"按系统识别的来"，只有用户选过的才进 `accountCurrencies`。
  预填一次就再也分不清"用户确认过 USD"和"系统猜了 USD"，日后改进识别逻辑也推不动已落盘的值——
  主体本位币那一处就是预填踩出来的坑。
- **覆盖按科目编码回退**。TB 与 JE 的科目名拼法不同（TB 是「编码 一级名 二级名」，
  JE 是「编码 科目文本」），界面上勾的是两边并集；只按全名匹配会让指定的币种只对一侧生效。
  `currency_for` 与 `role_for` 用同一套回退。
- **JE 的结论优先于 TB**。JE 逐行读凭证货币，TB 一个科目只有一行；`seen` 取两边并集。

验收：

```bash
cargo test --manifest-path src-tauri/Cargo.toml --test fx_currency_probe -- --ignored --nocapture
cargo test --manifest-path src-tauri/Cargo.toml --test fx_currency_override -- --ignored --nocapture
npx vitest run src/FxAuditPage.test.ts
```

**这一列改变不了 TB 本身没有按币种拆分余额这件事。** 指定币种能让科目进入测算范围，
但如果 TB 只给出该科目一个合计余额（同一应付账款下同时有 HKD 和 JPY），
按币种重估所需的原始数据依然不存在，结果仍是受限测算。

### 3.5 形态型号与整组匹配

角色表说的是"有哪些角色"，形态型号说的是"哪几个角色必须凑齐才算一张能用的表"。

#### TB 六型

| | 期初 | 期末 | 原币余额 | 本年本位币累计 | 本年原币累计 |
|---|---|---|---|---|---|
| **TB1** | 本位币净额 | 本位币净额 | — | 借＋贷 | 借＋贷（可选） |
| **TB2** | 方向＋本位币净额 | 方向＋本位币净额 | — | 借＋贷 | 借＋贷（可选） |
| **TB3** | 本位币借＋贷 | 本位币借＋贷 | — | 借＋贷 | 借＋贷（可选） |
| **TB4** | 本位币净额＋原币净额 | 本位币净额＋原币净额 | ● | 借＋贷 | 借＋贷（可选） |
| **TB5** | 方向＋本位币净额＋原币净额 | 方向＋本位币净额＋原币净额 | ● | 借＋贷 | 借＋贷（可选） |
| **TB6** | 本位币借＋贷、原币借＋贷 | 本位币借＋贷、原币借＋贷 | ● | 借＋贷 | 借＋贷（可选） |

六型共有：`entity`（可选）、`accountCode`（必填）、`accountName`（必填，可多列）、
`currency` 原币列（可选）、`currencyText`（可选）、`functionalCurrency` 本位币列（可选）、辅助信息（可选）。

> **TB1 隐含要求净额带符号。** 它没有方向列，负债科目的期末余额必须是负数，勾稽等式才成立。
> 客户导出绝对值时 TB1 无解——这才是 TB1 与 TB2 的实质区别，不只是"少一列方向"。

#### JE 三型

| | 方向 | 本位币金额 | 原币金额 |
|---|---|---|---|
| **JE1** | ● | 借＋贷 | 借＋贷（可选） |
| **JE2** | ● | 净额 | 净额（可选） |
| **JE3** | — | 净额 | 净额（可选） |

三型共有：`entity`／`date`／`id`／`accountCode`／`accountName`／`summary` 必填，
辅助信息、`voucherType`、`currency` 可选。

> **JE1 的方向列与借贷分列冗余。** 借贷分列本身已表达方向，两者可能矛盾。
> 定为**以借贷分列为准，方向列仅作校验，不一致时告警**。

#### 整组匹配：缺一不可

**一个型在某个槽位里声明的列，必须全部到齐才算命中该型。**
不是逐字段查必填——那样只能报"缺少必要字段"，说不清缺哪个。

| 规则 | 说明 |
|---|---|
| required 槽 | 该型声明的列全部到齐才算命中。缺任意一列 → 不命中 |
| **optional 槽同样整组** | 本年原币累计借＋贷两列，要么都给要么都不给。**只给借方 = 无效**，告警不放行 |
| 未命中任何型 | 取匹配度最高的型，报出**它缺哪几列**——"按 TB5 匹配，缺少『期初方向』" |
| **同时命中多型** | **优先借贷分列**（TB3/TB6、JE1）。借贷能推出净额，反之不行 |

最后一条对应 §3.11 里那个真问题：TB 形态 F、JE 金蝶完整版、JE AX／D365 三个不同 ERP 都是
"借贷两列与净额列同时给"，现行方案组要求二选一会判成不成立。按优先级取一种，不报错。

### 3.6 借贷符号方向判定

同一列"贷方发生额"，实务里有两种写法：写绝对值（语义靠列名承载），或者已经带负号。
两种都常见，**必须判出来**，判错了整表金额全错。

方法对 TB 和 JE 是同一个：**枚举符号假设，用勾稽等式的全表成立率裁决**，只是等式不同。

#### TB：用期末 = 期初 ± 借 ± 贷 反推

待定参数是"贷方性质的列取正还是取负"，记作 s ∈ {+1, −1}：

| 型 | 等式 |
|---|---|
| TB1 | 期末净额 ＝ 期初净额 ＋ 借方 ＋ **s**·贷方 |
| TB2 | 方向还原成符号后同 TB1，另加一个参数判**方向列是否已反映在金额里** |
| TB3 / TB6 | (期末借 ＋ **s**·期末贷) ＝ (期初借 ＋ **s**·期初贷) ＋ 借方发生 ＋ **s**·贷方发生 |
| TB4-6 原币 | 同上，**原币一套单独判**，不沿用本位币的结论 |

#### JE：用凭证内借贷平衡

| 型 | 等式 |
|---|---|
| JE1 | 每张凭证 Σ(借方 ＋ **s**·贷方) ＝ 0 |
| JE2 | 按方向还原符号后 Σ ＝ 0，另判**方向是否已反映在金额里** |
| JE3 | Σ ＝ 0，无待定参数，直接验证是否平衡 |

#### 裁决规则

- **逐行算、全表统计取多数**，不逐行判——个别行数据错不能翻盘
- 舍入容差：绝对 0.01 或相对 1e-6，取大者
- 两个假设都低于阈值（建议 95%）→ **报错"期末与期初＋发生额勾稽不上"**，不硬选一个
- 贷方发生额全为零 → 判不出，但也无影响，标记"未验证"

#### 真实数据上的判别度

拿汇兑损益测试资料里那份 SAP 科目明细（229 行）实跑：

| | 本位币 | 集团货币 |
|---|---|---|
| 期末 ＝ 期初 ＋ 借 **−** 贷 | **229 / 229 ＝ 100%** | **229 / 229 ＝ 100%** |
| 期末 ＝ 期初 ＋ 借 **＋** 贷 | 72 / 229 ＝ 31% | 80 / 229 ＝ 35% |

判别度足够大，不需要复杂的启发式。这份表期初 46 行负数、期末 76 行负数，
**净额确实带符号**，符合 TB1 的隐含要求。

#### 待补：原币的符号验不了

原币余额（TB4-6 的期初/期末）是必填，但**本年原币累计借贷发生额是可选**——
等式缺一项就没法验。二选一：把原币发生额也设为必填，或明确"原币符号沿用本位币结论"
（有风险，实务里两套列可能来自不同导出）。

### 3.7 业务台账：第三张角色表 + 四型整组匹配（2026-08-27）

借款利息的**借款台账**和**利率台账**读的不是 TB/JE，是业务台账——没有科目、
没有借贷方向。它们的角色**不进 TB/JE 标准表**，但已经收进同一个内核，
成为与 `je_roles()` / `tb_roles()` 并列的第三张表 `loan_roles()`，
共用 `alias_score`（最长命中、冲突词一票否决）与 `match_forms`（形态整组匹配）。

收编之前这里是 `loan_interest.rs` 里一份平铺关键词列表，有两个后果：

1. **前后端角色名不是一套**。面板下拉给的是 `closingPrincipal` / `maturityDate` /
   `fixedRate`，引擎识别出来的是 `outstanding` / `endDate` / `rate`，
   自动映射建议落不进格子，用户看到的就是"什么都没识别出来"。
2. **必填校验写死四项**（`loanId`＋期初本金＋期末本金＋利率类型），
   那是变动表的口径。测试集九份台账里六份是"合同本金＋起止日＋期末余额"，
   既没有期初列、利率也直接给数值没有类型列——**必然误报，台账模式点不动测算**。

现在必填由**形态**决定。借款台账四型（`loan_forms()`）：

| 型号 | 起算额（任一即可） | 起始日 | 终点 | 期间发生额 | 利率 | 选填 |
|---|---|---|---|---|---|---|
| A | 本金 ｜ 期初余额 | ✔ | 到期日 | — | ✔ | 利率类型 |
| B | 本金 ｜ 期初余额 | ✔ | 期限 | — | ✔ | 利率类型 |
| C | 期初余额 ｜ 本金 | ✔ | — | 本期新增＋本期归还 | ✔ | 利率类型 |
| D | 期末余额 ｜ 本金 | ✔ | — | 本期新增＋本期归还 | ✔ | 利率类型 |

判定优先级 **A ＞ B ＞ C ＞ D**（数组从弱到强排列，同分时后定义的优先）：
到期日是直接列示的，比拿期限推算准；既有到期日又有四栏时（04 深圳前湾）认 A 型，
四栏转为勾稽校验。九份真实台账全部命中 A 型，基线测试见
`loan_interest.rs` 的 `loan_form_tests`（跑 `cargo test --lib loan_form_tests`）。

**「任一即可」槽是这次为台账新增的槽型**（[`Form::any_of`]）：组内至少一个到位即满足。
起算额三兄弟——本金、期初余额、期末余额——都是"某个时点的占用本金"，
在"全期恒定"的假设下给任意一个都能起算，不必同时给。TB／JE 没有这种槽，两张表一律留空。

**无固定期限借款不纳入**：只有起算额＋起始日＋利率、既无到期日期限也无期间发生额的
那一类（股东借款、关联方拆借、集团资金池、循环贷、永续债）。
当前它落在"最接近 A 型、缺到期日"的未命中态，**不静默当成某一型放行**。
以后要纳入直接往表里加一型即可。

型号与槽位的**唯一定义在 Rust**，随 `loan.inspect` 的 `roles` / `forms` 字段下发；
前端 `src/loanForms.ts` 只实现排序与判定的纯计算（与 `match_forms` 同序），
不再自己抄一份型号定义。

#### 逐行利率口径在预览区确认（2026-08-28）

台账普遍**没有**「利率类型」列，利率列里混着 `3.85`、`0.0365`、`浮动`、`LPR+90BP`
好几种写法。引擎自己猜猜错了没人看得出来——整笔利息就那么算错了。
改成**默认值算给用户看、用户改得动、改完整份回传**：

- 默认值规则在 `src/loanRateTypes.ts`：**台账的「利率类型」列 → 利率列的写法**。
  利率列是纯数值（含 `%`、千分位、括号负数）就是固定；写了浮动字样
  （`浮`／`LPR`／`基准`／`挂钩`／`重定价`／`float`／`variable`）就是浮动；
  两者都不是（空值、「面议」）按固定处理，用户在预览区能看到并改。
- 台账预览区追加两列（`DataTable` 的 `trailingColumns`）：**利率类型**下拉，
  选了浮动才蹦出**上浮(+)/下浮(-) BP** 输入框。默认值随映射实时重算，
  用户的手工改动单独存、叠在默认值上面，两者互不覆盖。
- 整份回传为 `ledgerRateOverrides`，下标 = 台账数据行序。因此**台账的预览行数
  从 8 行放宽到整表**（上限 2000）——只给 8 行的话第 9 行往后没法设置。
  TB／JE 仍是 8 行。
- 浮动的基准取值顺序：**台账的基准利率列 → 利率列的数值 → 内置 LPR 报价表**（`lpr.rs`）。
  台账把 `0.037` 写在利率列、另有一列写「浮动」是最常见的写法（07 星衡），
  这时 `0.037` 就是基准；只写「浮动」两个字、不给数值的才查 LPR。

#### 内置 LPR 报价表（`lpr.rs`）

只存**利率发生调整的日期**（LPR 每月 20 日报价，绝大多数月份与上月持平），
查询取「不晚于定价基准日的最近一次调整」——利率结果与逐月存完全一致，
所以 Sheet 的日期列写的是「利率调整生效日」，不是「那天恰好有报价」。

- **定价基准日 = max(起息日, 报告期初)**。真实重定价日各家合同不同，这是简化，
  所以底稿把这个日期单独列一列、基准利率写成引用它的公式，用户改日期就重算。
- **品种按期限选**：超过 5 年用「5 年期以上」，否则用「1 年期」。
  «5年期以上» 取字面含义，**整 60 个月不算**；比较按月加减而非数天数，
  否则闰年会让同为 60 个月的两笔借款落到不同品种。
- **两条不硬算的边界**：定价基准日早于 2019-08-20（LPR 改革之前，挂的是央行基准
  贷款利率）→ 不套 LPR，标待复核；晚于 `QUOTES_THROUGH` 数据截止日 → 用最后一期
  报价给出完整草稿，同时标待复核并提示补录。
- **数据是默认值不是权威**：表照训练知识录入、未经联网核对，注释与 Sheet 抬头都写明了，
  正式出具前要对照官方公告核。补录新报价时 `QUOTES` 按日期升序插行、
  `QUOTES_THROUGH` 跟着改。

#### 底稿里三列是活公式

导出的 `借款变动与利息测算` 表新增「定价基准日」「LPR品种」「计息本金天数」三列，
并把**基准利率、有效年利率、测算利息**写成公式：

- 基准利率 `=INDEX(LPR报价表!$B:$C, MATCH(定价基准日, LPR报价表!$A:$A, 1), 品种列)/100`
- 有效年利率 `=IF(利率类型="浮动", 基准利率＋加减点/10000, 固定利率)`
- 测算利息 `=计息本金天数 × 有效年利率 ÷ 365`

利息能写成公式，是因为分段计息里利率是常数，
`Σ(本金ᵢ×天数ᵢ) × r ÷ 365` 与逐段累加等价——所以把 `Σ(本金×天数)` 落成一列就够了。
这样**在「LPR报价表」改一个格子，基准利率、有效利率、利息一路重算**。
内置表迟早会过期，过期时用户必须能自己修，而不是拿到一份看不出哪里错了的死数。
`LPR报价表` Sheet 无论有没有行用到 LPR 都会写出来。

界面上的测算期间也一并收敛：**只填资产负债表日**，期间开始由它推出所属年度年初
（`loanReportStart`，与存款利息 `depositReportStart` 同一口径），不再要求填两个日期。

其余角色（`lender`、`loanStatus`、`repaymentMethod`、`benchmarkRate`、`spreadBps`、
`remark` 等）仍可映射，只是不参与形态判定——出表、复核提示、利率推算要用。
历史保存的旧名（`outstanding` / `maturityDate` / `fixedRate` / `benchmark`）
由 `migrate_role_name("loan", …)` 读回来。

但要注意：**借款利息的 TB/JE 映射里那几个角色其实是标准角色的业务别名**，应当归并——

| 借款利息现名 | 归入 | 表 | 理由 |
|---|---|---|---|
| `openingPrincipal` | `openingFunctionalCredit` | TB | 就是期初贷方余额 |
| `closingPrincipal` | `closingFunctionalCredit` | TB | 就是期末贷方余额 |
| `periodDebit` / `periodCredit` | `periodFunctionalDebit` / `Credit` | TB | 同义，改作完整性校验基准（见 §3.9） |

`loanId`（借款标识）**保留为借款利息的专属角色，不并入标准表**。
它原本要并进的通用 `auxiliary` 已经删除（见 §3.8）——语义含糊的通用字段换成
语义明确的专属字段，正是这次收敛想要的方向。

### 3.8 已确认删除的角色

下面这些角色曾经存在于某个工具的映射表里，经逐个核查代码使用点后确认删除。
记录依据，避免以后有人凭直觉再加回来。

| 角色 | 原属 | 判定 | 依据 |
|---|---|---|---|
| `period` 会计期间 | JE | **从未被读取，还制造了假选项** | 全代码只有一处读 `period`，且在只有 TB 会走到的分支里；JE 一律走 `date` 列。更糟的是存款利息前端把它当成"记账日期或会计期间"二选一放行，后端却硬性要求 `date`，只映射会计期间的用户会在点下测算后才撞上"序时账尚未映射记账日期"——**这是现存的一个前后端不一致缺陷**，删掉 `period` 顺带解决 |
| `period` 会计期间 | TB | **有用途，但不该占映射格子** | 唯一用途是从"会计期间"列抠出年份做期间校验。汇兑损益根本没有这个角色，它直接扫描所有表头含"期间"的列就完成了同一件事——改由内核自动探测，不必让用户手工确认 |
| `periodAmount` 本期有符号发生额 | TB（存款利息） | **死字段** | 只在角色表和前端标签里定义，代码中没有任何读取点，连候选打分的加成列表里都没有它 |
| `auxiliary` 辅助核算 | JE ＋ TB | **语义含糊的通用字段，删除** | 三个工具用它做三件不相干的事：汇兑损益只拿它做余额键（重估按科目＋币种算，带不带它结果一样），存款利息拿它认存款档次和银行账户，借款利息拿它当借款标识。一个字段承担三种语义，映射时用户也说不清该填什么。删掉通用角色，需要的工具改用语义明确的专属角色（见下） |
| `clearingId` 清账号 | JE（汇兑损益） | **死字段，已删** | 映射后从未被任何业务逻辑读取，2026-08-22 已随科目拆分一并删除 |

**删掉 `auxiliary` 之后，两个工具需要各自的专属角色顶上：**

| 工具 | 原来靠 `auxiliary` 做的事 | 替代 |
|---|---|---|
| 存款利息 | 用"科目名＋辅助核算"认存款档次；把序时账每笔落到具体银行账户 | 新增专属角色 `bankAccount`（银行账户），语义明确，只在存款利息启用 |
| 借款利息 | 区分同一科目下的不同笔借款 | 沿用它已有的 `loanId`（借款标识），不并入标准表 |
| 汇兑损益 | 只进余额键，重估结果不受影响 | 无需替代。TB 按明细拆行时靠"同键多行自动合并"处理 |

两个专属角色都不进通用标准角色表——**通用表只放五个工具语义一致的字段**，
这正是删掉 `auxiliary` 的目的。

### 3.9 保留但按工具启用的角色

**角色留在标准表里，不等于每个工具都要用它。** 下面三个都是先前被质疑过的，
逐个核查后的结论是：它们各自只在一部分工具里是关键，其余工具不启用即可。

#### `voucherType` 凭证类型 —— 仅汇兑损益，非必填

只有汇兑损益定义了这个角色，存款、借款、看账都没有，而且它不在必填清单里。
它的用途是分类判断：`FX`/`AB` 判自动重估，`DZ`/`ZE` 判结算，`!= AB` 参与"简单结算"判定。
没有它分类会退化，但不阻断测算。

#### TB 本期发生额 —— 永远只作校验基准

**测算主路径全靠序时账**，TB 发生额不参与推算。它的唯一定位是"客户账面记了多少"，
用来跟测算结果比出差异：

| 工具 | 拿它比什么 | 缺失时 |
|---|---|---|
| 汇兑损益 | 账面已入账的汇兑损益 ↔ 测算结果 | 回退到期末累计金额，底稿写明取数口径 |
| 存款利息 | 账面已入账的利息收入 ↔ 测算结果 | 回退到期末余额净额，底稿写明取数口径 |
| 借款利息 | TB 本期贷方／借方 ↔ 序时账汇总出的新增／还款 | 无法校验，该笔借款列为未匹配 |

借款利息这一条是本次修正的重点。**原来的做法是：序时账匹配不上时，改用 TB 发生额
把利息算出来**，行上标"待复核"、`match_basis` 写"未匹配 JE，采用 TB 发生额"。
标记是有的，但结果里仍然多了一个用另一套数据算出来的利息数。

**改为：序时账匹配不上就不出数。** 该笔借款进"未匹配"清单，利息留空，
其余借款照常测算——一笔对不上不该让整张表算不出来，但也绝不能拿替代数据凑一个数出来。
TB 发生额在这里的正当用途是反过来的：**用它校验序时账是否完整**，
序时账汇总出的新增／还款与 TB 发生额不符就报出来。

所以它是**可选角色**，且永远不作测算输入。

汇兑损益的代码注释里还记着一次踩坑——"发生额借、贷方案只有在两列同时映射时才成立，
否则 SAP 的 MTD 列会误替代 YTD"，说明这个字段要成对映射才安全。

另外澄清：**TB 从来就没有原币发生额**。原币口径在 TB 上只有期初与期末余额六件套，
本期发生额只有本位币一个口径。

#### 抽查结论：集团模板高度一致

对 22 份 Oracle 集团序时账（覆盖 20+ 家公司、中日韩马印港法墨沙特等 8 个国家地区）
逐份比对表头，**只有 2 种签名，差别仅在多一列 `Description`，其余 37 列完全相同**。

同样地，Oracle 的分月 TBD 与全年 TBD 两份表头完全一致。

**含义**：集团口径的样例只需针对模板做一次映射规则，就能覆盖所有子公司；
真正的形态风险来自不同 ERP（金蝶、用友、AX／D365、SAP、Oracle）之间，
以及同一 ERP 的不同导出方式（金蝶就有"凭证字＋凭证号"两列和"凭证字号"一列两种）。

#### 还需要补的样例类型

多期间横向展开（1–12 月各一组余额）、合并层含抵销分录列、浪潮／SAP B1 导出、
带辅助核算的明细余额表。**这份清单是开放的**，角色表定稿的标志是
"手上所有真实样例都能只靠这张表映射出来"。

### 3.12 字段库

**字段库不是一张别名表，是五样东西：**

| 组成 | 作用 |
|---|---|
| 角色清单 | JE 一份、TB 一份，见 §3.2／3.3 |
| **别名库** | 每个角色在实务中的所有写法，中英文都要 |
| **冲突词库** | 防止短别名把别的列吃掉——这是现有实现最大的坑 |
| 数据形态判定 | 列名天生分不出时看数据 |
| 歧义清单 | 判不了就让用户确认，不猜 |

#### 覆盖率验证

拿 §3.11 那 12 种真实形态的**全部 129 个列名**，逐列标注"应该落到哪个角色"，
再跑现有别名库和补充后的字段库：

| | 正确 | 认不出 | 映射错 | 噪声命中 |
|---|---|---|---|---|
| 现状（`fx.rs` 里的别名库） | **76 / 129 ＝ 59%** | 39 | 12 | 2 |
| 字段库 v2（补别名＋冲突词） | **127 / 129 ＝ 98%** | 0 | 2 | 0 |

剩下那 2 条是同一个问题——`货币` 与 `Currency` 光看列名分不出是本位币还是原币，
而这正是 §3.4 该管的：填满且唯一才是本位币列，其余都是原币列。
按 §3.4 判定后实际有效准确率是 129／129。

**验证脚本可复用**：每收到一份新形态的样例，把它的列名和标准答案加进去跑一遍，
准确率掉了就说明别名或冲突词要补。建议固化成回归测试。

补别名之前，先得修这两个——它们让"补别名"这件事本身失效：

| 缺陷 | 现象 | 修法 |

| 短别名把长列名吃掉 | `functionalCurrency` 的别名"本位币"吃掉了 `期初金额-本位币`、`借方金额-本位币`、`期末金额-本位币`——SAP 那份 TB 的**所有金额列**都被判成"本位币字段" | 给它加冲突词 `金额／余额／balance／amount／发生／差异` |

| `foreignAmount` | 原币金额、外币金额、凭证金额、原币、`Document Currency Value` |
| `foreignDebit` / `Credit` | 原币借方／贷方、外币借方／贷方、货币借方金额、货币贷方金额、`Enter Debits`／`Enter Credits` |

#### 冲突词库

| 角色 | 冲突词 | 挡住什么 |
|---|---|---|
| `functionalCurrency`、`currency`（TB） | 金额、余额、balance、amount、发生、差异 | `期初金额-本位币` 之类的金额列 |
| `accountCode` | desc、description、名称、文本、flexfield、segment | `Account Desc`、`Accounting Flexfield` |
| `accountName` | flexfield、segment、code | `Accounting Flexfield`、`Account Code` |
| `currency`、`functionalCurrency`（JE） | 金额、amount、value | `Document Currency Value` |

#### 数据形态判定（列名不够用时）

| 判什么 | 怎么判 |
|---|---|
| 币种列是本位币还是原币 | 归一化取值后：种类 > 1 即原币列；填满且唯一才是本位币列。完整规则见 §3.4 |
| 科目编码 vs 科目名称 | 编码列取值形如字母数字编码；名称列是可读文本 |
| 哪一套科目跟 JE 对得上 | Oracle 那种 `Account` 与 `SL Account` 并存的表，**由跨表对齐用实际取值决定用哪套，两套都对得上就都用** |
| 日期列 | 可解析为日期的比例 |
| 金额列 | 数值占比 |

## 4. 校验也按表类型分开

### 4.0 先立一条通则：对不上就报出来，不拿别的数据凑

审计工具出的每一个数，都要说得清是从哪来的。**数据对不上时，正确的动作是把它报出来，
而不是换一套数据源算出一个数**——哪怕旁边标了"待复核"，那也是一个会被读进底稿的数字。

判断一个回退能不能接受，看它换的是"取数途径"还是"结论依据"：

| | 例子 | 判定 |
|---|---|---|
| **可接受**：同一业务含义的两种取数途径，且底稿写明用了哪种 | 损益科目的本年累计金额，既可以取本期发生额，也可以取期末余额 | 保留 |
| **不可接受**：换一套数据源算出结果，结论的依据变了 | 借款利息在序时账匹配不上时改用 TB 发生额算出利息 | **改掉**，见 §3.9 |
| **正确示范** | 存款利息把序时账分录落到银行账户：能唯一确定就落，落不准且候选多于一个就跳过留待复核，不猜 | 照此办理 |

按这条通则，本次要改的是借款利息那处；存款利息落账那处本来就是对的，可以当模板。

---

校验规则跟角色一样，不混在一起。三类各自独立：

### JE 专属校验
- 凭证唯一键（主体＋日期＋凭证识别字段）无空值
- 无完全重复的明细行
- 金额方案组成立：本位币一组；启用原币口径时，原币也要一组
- 数据期间与报告期一致

### TB 专属校验
- 期初、期末至少各有一组余额（净额 或 借＋贷）
- 同一余额键（主体＋科目＋币种）的多行**自动合并**，不再报错
- 余额列的有效数值比例达标
- 币种来源可确定：有交易币种列，或能从科目名称／币种线索文本里认出外币科目
- 与 JE 同时使用时，期初与期末要有一组同口径余额（原币对原币，或本位币对本位币）

### 跨表校验（仅在两表都上传时）
- 作用域**只有 §2 那 3 个共用角色**，实际核 `accountCode` 与 `accountName`
- 按实际取值比对重合度；对不上则在两张表的低基数列之间自动搜索能对上的列并改映射
- 编码与名称至少一个对得上才放行，两个都对不上才拦截

## 6. 三层架构

### 第一层：标准角色词汇表（纯数据）

**两份清单，JE 一份、TB 一份**，共用角色在两份里各出现一次（不抽公共段，
避免归属不清）。每个角色记：标准名、中文标签、别名、冲突词、能否多列、
是否必填、属于哪个方案组、属于哪个币种口径。

### 第二层：后端映射内核（新增模块）

**入口按表类型分**：`inspect(source, Je)` / `inspect(source, Tb)`，
各自取自己的角色集和校验集，互不引用。工具只声明"我这张 JE 要哪几个角色、
我这张 TB 要哪几个角色"。

**共用的是机制，不是角色**：

- 读表与表头探测（含大文件轻量路径、Excel 日期格式还原、两层表头合并）
- 按别名＋数据形态给每列打分，生成候选与建议映射
- 映射列存在性、方案组互斥、必填这三类通用校验的执行框架
- LLM 复核提示词**从角色清单自动生成**——现在每套一段手写提示词，
  是角色改名后最容易忘记同步的地方

**跨表对齐是独立的一块**，不属于 JE 也不属于 TB，只在两表都存在时运行，
作用域限定在 3 个共用角色（已在汇兑损益里实现，本就是通用逻辑）。

**数据年度探测收进内核**：TB 的年度不再依赖 `period` 角色，改为扫描所有表头
含"期间"的列自动推断（汇兑损益的现成做法），用户不必为此手工映射一列。

### 第三层：前端统一映射面板

一个组件，但**JE 面板与 TB 面板各渲染一次**，下拉里只出现该表类型的角色，
不会让用户在序时账里看到"期末余额借方"这种选项。组件负责：表头下拉选角色、
多列角色、方案组互斥置灰、必填提示、LLM 复核、口径核对结果展示。

角色的中文标签由后端随识别结果一起下发，前端不再各自硬编码一份
（现在改一个标签要改两处，容易漂移）。

## 7. 迁移步骤

每步独立可验收，随时可以停在任一步。

| 步骤 | 内容 | 为什么是这个顺序 |
|---|---|---|
| 0 | **穷举 TB 形态**，用真实样例验证角色表 | 见 §3.11。TB 形态比序时账散得多，角色表没经过真实样例检验就定稿，后面每碰到一种新形态都要返工 |
| 1 | 定 JE 与 TB 两份角色词汇表 | 命名先对齐。就是本文 §3，但要等第 0 步验证过 |
| 2 | 抽出后端内核，**汇兑损益**先切 | 它最完整、两种表都有，测试护栏最厚，切它能最快暴露内核抽象是否够用 |
| 3 | **存款利息**切过来 | 已经在复用汇兑损益的表结构，改动最小；顺带白拿科目拆分、币种新规则、跨表对齐 |
| 4 | **借款利息**切过来 | 要换掉自有读表，并把 TB/JE 角色归并到标准名；测试最薄，**动之前先补测试** |
| 5 | **看账＋正负数**切过来 | 只有 JE，不涉及 TB 那半边；但在 `tabular.rs` 里，要把固定字段的 struct 改成通用映射，且等并行修改停手 |
| 6 | 前端四套界面合并 | 后端契约稳定后再动 UI 最省事 |

## 8. 风险与护栏

**角色改名会让历史任务参数失效。**
任务历史里存着旧角色名的映射参数，改名后读不出来。
处理办法是加兼容层：读参数时把旧名翻译成新名。
汇兑损益这次的 `account` → `accountCode`＋`accountName` 已经验证过这个手法可行
（见 `fx.rs` 的 `account_columns`），照搬即可。

**借款利息的测试太薄。**
截至 2026-08-22，四个模块的测试数量差距明显，借款利息是唯一需要"先补护栏再动"的。
现场核对：

```bash
for f in fx deposit_interest loan_interest tabular; do echo "$f: $(grep -c '#\[test\]' src-tauri/src/$f.rs)"; done
```

**`tabular.rs` 存在并行修改。**
第 4 步动它之前必须确认没有其他会话正在改，否则冲突难解。

**每步都要跑各自的验收矩阵。**
汇兑损益没有 `*_PARITY.md`（它是新工具，不是迁移工具），
但有真实客户样例的 `#[ignore]` 测试，改动后必须显式跑：

```bash
cargo test --manifest-path src-tauri/Cargo.toml fx::tests -- --ignored
```

看账那部分要同步更新 `KANZHANG_PARITY.md`。

## 9. 怎么算做完了

- JE 与 TB 各有一份角色清单，五个工具都从这两份里取，没有任何工具自带私有角色表（业务台账角色除外）
- 序时账的映射界面里不会出现余额类角色，科目余额表的界面里不会出现凭证类角色
- 候选打分、必填校验、方案组校验、LLM 提示词各只有一份实现
- 跨表对齐是独立一块，作用域限定在 3 个共用角色，不含币种
- 每个角色都有实际读取点；新增角色前先确认它会被业务逻辑用到
- 中文标签只在一处定义
- 新增一个需要读账表的工具时，只需声明角色，不需要复制任何映射代码
- 全量测试通过，四个真实客户样例测试通过

## 10. 2026-08-28 公共复核生命周期与业务覆盖口径

- `LedgerReviewAll` 以数据源标识和复核代次隔离异步结果；切换文件、重新识别或组件卸载后，旧请求不得回写到新映射。存款、汇兑和 FA 直接使用同一组件与同一公共 TB/JE 复核入口，不建立工具专属提示词。
- 存款科目角色拆为“自动分类结果”和“用户覆盖”两层。自动排除不等同于用户排除；父科目人工分类可以向未人工覆盖的末级科目继承，末级明确排除优先。
- 公共一致性测试使用合成 TB/JE 核对汇兑、存款、看账和 FA 的 Sheet、标题行、映射、标准净额与符号结论，避免依赖客户文件。看账与 FA 的正负数 Net=0 状态来自同一个公共函数。
- 借款台账已有执行利率时，默认类型为固定利率并保留该执行利率；只有用户明确改为浮动利率，才清空固定执行利率，改按公共识别的基准利率加减点计算。没有独立基准时使用对应期间 LPR 回退并提示复核，不得把原固定执行利率当作浮动基准。
