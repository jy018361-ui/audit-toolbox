# OCR 独立工具验收约定

## 2026-10-28 · 自然语言要求和自动Excel列

所有场景直接支持中文自然语言要求，不强制先选自定义。默认界面只显示业务关注、行粒度和缺失信息处理；维护中的原场景提示词、协议及财务案例核验保留为内部执行指南，不改AudiPick的全局规则。自定义场景不再强制信息类别/摘录内容两列。旧保存模板的字段/输出段只做可读投影，保留业务条件与末尾追加要求；默认模板和其他项目不被编辑污染。历史非空汇总阶段继续在内部使用，空汇总回退维护规则，不阻塞单一需求框。

返回可声明业务列名及顺序，未指定时自动安排；新增列仍必须有实际记录中的同名字段，不能声明一套列而把值塞入另一套字段。非法/重复/内部协议列经有界修复仍失败则拒绝，不导出空表冒充成功。校验之后才按业务列投影，保留独立来源字段和隐藏核验数据，避免原生导出追加非用户列。无列声明的旧返回按实际出现字段推导，不补大量默认空列。并发响应按请求源序确定列顺序；小范围业务要求不触发默认全范围漏项补充，但每条原文证据/主体/同意义务仍严格核验。请求失败及未完成结果的既有处理不变。

回归命令：`npx vitest run src/ocrRequirements.test.ts src/ocrScenarios.test.ts src/OcrPage.test.tsx`、`npm run build`。真实测试包括内置场景短样本及两项自然语言指定/自动列样本，最后用捕获响应对当前生产引擎回放，再以隔离数据库调用原生Excel导出并回读全部业务值、来源页码、证据及前导零。浏览器检查所有场景默认无JSON/协议、命名重选和宽窄布局。数据只在忽略目录 `artifacts/ocr-natural-requirements-20261028/`，不改用户项目或凭据；这是自然语言交互/输出协议验收，不代替任意长文逐条人工审阅。

## 2026-10-28 · 扫描件缩放与手写印章诊断

分页左侧预览提供50%–400%缩放及适应宽度；翻页保留比例、滚动回到左上，切换文件重置。只改变CSS显示宽度，识别输入字节及复制原文不变；图片未加载时禁用。阅读视图/页面/源图回归及1440/900/390浏览器布局通过，命令 `npx vitest run src/OcrReadingView.test.tsx src/OcrPage.test.tsx src/ocrSource.test.ts`、`npm run build`，记录在本机忽略目录 `artifacts/ocr-preview-20261028/`。

东风合同第2/4页的保存结果已漏手写姓名和印章；相同qwen3.5-ocr的原生文档解析重测（Poppler按2600长边渲染，不声称与PDF.js像素一致）显示第4页原始text及layouts都没有印章文字。两个局部区域追加兼容接口自定义关注要求，共四次真实调用，手写和方章读出部分缺失信息，但圆章仍漏、姓名顺序及地址仍有误读。该诊断证明不能靠文本解析或场景prompt恢复未识别内容，尚不构成自动补读的准确率验收；模型/设置/真实项目不改、不自动合并诊断响应。自然语言需求与内部协议分离的交互本轮仅讨论。

本工具参考 AudiPick 的服务适配、场景定义和财务契约证据核验；项目、源文件副本、分页校对和摘录结果使用独立存储，不迁移或改写 AudiPick 项目。

## 不包含的既有专用工作流

旧版因结构失败而未保存的正文无法从现有 Excel/分页记录补回；清理协议内容不等于完整识别，需对原扫描件重新识别。HTML 合并单元格展开为原行列空位，保留左上格文字并提示核对，本轮不承诺复刻所有版式。原始响应不通过普通页面或 Excel 展示。

不复制 AudiPick 的收入审阅底稿套用、合同关系分组、项目备份和案例库维护界面。跨页表格分别保留，不自动推断合并；输出以完整文字、可编辑行列和来源定位为目标，不复制印章、手写签名或扫描版式。模糊、缺损文字和表格仍需人工校对。

## 2026-10-28 场景输出协议与真实模型验证

通用借款原模板要求合并多个非连续条款到`excerpt`，且既有JSON示例只有`items`；OCR追加的连续逐字引用和`coverage_complete`要求与其产生冲突。真实Dev模型又将“本轮检查完整”误解为“整份借款商业要素齐全”，在缺少后续页/附件时返回false。修复保持严格校验，改用L行号回填，补齐协议字段类型、分段草稿语义；不是将false强行变true，也不接受近似引用冒充逐字证据。

## 2026-10-28 网络分段诊断

后续路由核实与结论纠正：用户要求继续统一交给 Clash 分流，未要求强制走境外节点或在工具内硬编码国内直连。只读查询正在运行的 Mihomo 控制器确认 `mode=rule`、混合端口 7897；对百炼域名做一次不带凭据的 HEAD 连通性请求，并从 `/connections` 观察到 `host=dashscope.aliyuncs.com`、`type=HTTPS`、`rule=RuleSet`、`rulePayload=direct`、`chains=[DIRECT]`。本机同时启用 TUN，因此 curl `--noproxy` 只代表绕过 HTTP 代理入口，不能保证绕过 Clash/TUN，之前默认入口与跳过入口的耗时对比不能用来证明“境外代理节点拖慢百炼”。该 HEAD 检查没有调用模型、没有更改配置，只证明检查当时此域名的规则及出口，不反推早前每次连接的路由。生产 LLM/OCR/语义 HTTP 请求保留默认代理继承，未新增强制直连；代码中既有 `no_proxy` 仅出现在百炼 ASR 本机测试夹具。

用户反馈 Dev.6 扫描时单页识别调用约 23–41 秒，后台排队接近零。只读确认模型仍为 `qwen3.5-ocr`，本机同时配置系统代理及 HTTP/HTTPS/ALL_PROXY 环境变量，代理地址 `127.0.0.1:7897`。未据此断言 GUI 的实际路由；后续网络探针的默认 curl 路径使用现有代理环境。

`probe_ocr_network.py` 在随机本机回环端口接收原生 worker 的真实标准化图片请求，用隔离数据库与合成响应取样；凭据仅留在内存与 curl 标准输入，不写命令行、报告或磁盘。真实请求体在临时目录内供 curl 读取，退出后清除。使用 Windows curl 8.10+ 的累计计时拆分 DNS、TCP、TLS、上传、上传后等待及接收；早于上传结束的响应不生成虚假的负等待时间。此工具仅供开发诊断，运行会产生真实 OCR 费用，不是应用依赖。默认不重试；`--route direct` 仅对单次 curl 请求跳过代理，不改系统或应用设置。分段定义参见 [curl 官方手册](https://curl.se/docs/manpage.html)。

手工命令（仅用于已授权图片；先等待用户其他识别任务结束）：

```text

python scripts/probe_ocr_network.py --worker-exe <原生程序EXE> --settings-db <该通道SQLite路径> --image <同一页面PNG> --output <另一新目录> --levels 1,5 --repeats 2 --route direct
```

本次以可孚合同第 2 页测默认代理、直连各两轮单请求与五并发，再追加一轮代理五并发。各路由捕获的请求体 SHA256 相同，约 1.8 MiB，不改图像、提示词或模型；所有请求成功且无 429。代理五并发批次耗时 13.44／9.49／8.26 秒，直连 10.02／6.94 秒。五并发样本的上传中位数代理 4.462 秒、直连 2.607 秒；上传后等待中位数分别 3.826／3.995 秒，接收结果约毫秒级。两路径均波动，测试顺序为代理两轮→直连两轮→代理复查，不是随机交错严格基准；不能认定代理是唯一原因，更不能将上传后等待全部算作服务端计算。curl 与应用分别使用 Schannel 与 reqwest/rustls，探针用来检查传输链路，不能冒充安装版完整端到端耗时。

## 2026-10-28 · 真实长合同广义限制性流程

普通短场景验证不能代替广义限制性长文验证。限制性场景从12k串行大段改为约4k有界段、最多两段并发；页内长段保留重叠及全文义务主句，正文角色/出处仍按本段行号严格核验。进度按已通过的段数单调增加，返回乱序按来源合并，网络/取消不自动重试，失败停止后续派发且等待在途请求终止后再退出，整份未完成不当完整结果保存。

每次运行追加专属runtime契约，包括用户旧保存/命名提示词；缺字段、越界、未完成仍拒绝。若完整性已确认但只有部分记录不通过证据校验，保留已通过记录，仅请求修复坏行后合并复验，不因无后果而丢掉义务。完整性false不盲目转换true，不用空数组绕过。无源事先同意推断、其他义务代替送达地址提前通知等均有回归。官方Qwen思考开关和明确超时错误由公共LLM适配器处理，详见AUDIPICK_PARITY对应记录。
